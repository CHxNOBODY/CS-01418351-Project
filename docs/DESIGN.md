## 1. โปรแกรมนี้ทำมาเพื่ออะไร

### 1.1 ปัญหา

คอมพิวเตอร์สองเครื่องอยู่บนเครือข่ายเดียวกัน — Wi-Fi ที่บ้าน โต๊ะแล็บ หรือ hotspot
จากมือถือ — เครื่องหนึ่งมีไฟล์ที่อีกเครื่องต้องการ วิธีที่คนทั่วไปใช้กันนั้นมีข้อเสีย
ชัดเจนทุกวิธี:

| วิธีที่ใช้กันทั่วไป | ปัญหาที่แท้จริง |
| --- | --- |
| ส่งอีเมลหาตัวเอง | จำกัดขนาดไฟล์ และไฟล์ต้องผ่านเซิร์ฟเวอร์ของบุคคลที่สาม |
| Cloud drive / แอปแชต | อัปโหลดขึ้นอินเทอร์เน็ต แล้วดาวน์โหลดกลับลงมา เพียงเพื่อย้ายไฟล์ในระยะสองเมตร ต้องมีบัญชีและต้องมีเน็ตที่ใช้งานได้ |
| USB flash drive | ต้องเดินไปเสียบเอง ช้า และตัวแฟลชไดรฟ์เองก็เป็นช่องทางแพร่มัลแวร์ |
| Windows file sharing (SMB) | ใหญ่เทอะทะ ต้องตั้งค่า domain/workgroup และเป็นบริการที่ทุกคู่มือความปลอดภัยบอกให้ปิดไฟร์วอลล์กั้นไว้ |
| `ftp` / `python -m http.server` | ส่งเป็น plaintext ใครก็ตามที่อยู่บน Wi-Fi เดียวกันอ่านไฟล์ได้ และถ้าเป็น FTP ก็อ่านรหัสผ่านได้ด้วย |

**KUFT (Kasetsart University File Transfer) คือคำตอบที่เล็กและตรงไปตรงมา:**
พิมพ์คำสั่งเดียวในแต่ละเครื่อง ไฟล์วิ่ง **ตรง** ระหว่างสองเครื่องผ่านเครือข่ายภายใน
ถูกเข้ารหัส ทั้งสองฝั่งพิสูจน์ตัวตนซึ่งกันและกัน และข้อมูลที่รับมาถูกตรวจสอบด้วย
checksum เชิงวิทยาการรหัสลับก่อนที่ไฟล์จะถูกส่งมอบให้ผู้ใช้

### 1.2 ตัวโปรแกรมประกอบด้วยอะไรบ้าง

เป็น **โปรแกรมรับส่งไฟล์แบบ client/server** ที่ประกอบด้วย

* **โปรโตคอลชั้น Application** ชื่อ KUFT/2.0 ซึ่งออกแบบขึ้นเองและกำหนดไว้ใน
  `docs/KUFT-2.0-spec.md`
* **เซิร์ฟเวอร์** ที่แชร์ไดเรกทอรีเดียวและไม่ให้เข้าถึงอะไรที่อยู่เหนือขึ้นไป
* **ไคลเอนต์** ที่มี shell แบบโต้ตอบ (`ls`, `cd`, `get`, `put`, `rm`, `mv`, `rn`,
  `mkdir`, `stat`) และโหมดคำสั่งเดียวจบสำหรับเขียนสคริปต์
* **กลไกการจับคู่ (pairing)** ที่ให้การพิสูจน์ตัวตนแบบสองทาง โดยไม่ต้องพึ่ง
  certificate authority, directory service หรือบัญชีคลาวด์ใด ๆ ทั้งสิ้น

### 1.3 เป้าหมายการออกแบบ เรียงตามลำดับความสำคัญ

1. **ถูกต้อง** — ไฟล์ที่ไปถึงต้องเหมือนไฟล์ต้นทางทุกไบต์ ไม่เช่นนั้นการโอนย้าย
   ต้องล้มเหลวอย่างเห็นได้ชัด ไม่มีเส้นทางที่ข้อมูลเสียหายแบบเงียบ ๆ
2. **เป็นความลับและพิสูจน์ตัวตนได้** — ผู้โจมตีที่อยู่บน Wi-Fi เดียวกันต้องอ่าน
   ข้อมูลไม่ได้ และปลอมเป็นฝั่งใดฝั่งหนึ่งไม่ได้
3. **เล็กพอที่จะเข้าใจได้ทั้งหมด** — รวมทั้งโครงงานไม่ถึง 4,000 บรรทัด รูปแบบ
   ข้อมูลบนสายพอดีหนึ่งหน้ากระดาษ และอ่านได้จาก packet capture โดยตรง
4. **ใช้งานได้ด้วยคำสั่งสองคำสั่ง** — ถ้าต้องอ่านคู่มือก่อนใช้ ก็ถือว่าล้มเหลว
   ตามโจทย์ที่ตั้งไว้เอง
5. **ใช้ทรัพยากรจำกัด** — โอนไฟล์ 40 GB ต้องใช้หน่วยความจำเท่ากับโอนไฟล์ 4 KB

### 1.4 สิ่งที่จงใจไม่ทำ

การระบุข้อนี้ไว้ชัด ๆ ทำให้การออกแบบซื่อสัตย์ต่อขอบเขตของตัวเอง:

* **ไม่ใช่เครื่องมือ sync** ไม่มีการแก้ conflict ไม่มี versioning ไม่มีการเฝ้าดู
  การเปลี่ยนแปลง มันย้ายไฟล์ที่ระบุชื่อ หนึ่งครั้ง เมื่อถูกสั่ง
* **ไม่รองรับหลายผู้ใช้** มีรหัสจับคู่เดียว ระดับความไว้วางใจเดียว ไม่มีบัญชีผู้ใช้
  ไม่มีสิทธิ์รายไฟล์ ไม่มีการระบุตัวตนใน log
* **ไม่ได้ออกแบบให้เปิดสู่อินเทอร์เน็ต** ออกแบบสำหรับ LAN แม้จะไม่มีอะไรห้าม
  ไม่ให้ทำงานข้ามอินเทอร์เน็ต แต่ NAT traversal, service discovery และการเพิกถอน
  สิทธิ์อยู่นอกขอบเขตทั้งหมด
* **ไม่ใช่ VPN หรือ tunnel** มันโอนไฟล์ และทำเพียงเท่านั้น

### 1.5 ทำไมต้องมีเวอร์ชัน 2

KUFT/1.0 คือฉบับร่างแรกที่ไร้เดียงสา และทุกการเปลี่ยนแปลงใน 2.0 คือการแก้สิ่งที่
1.0 ทำผิด:

| KUFT/1.0 | KUFT/2.0 | ความล้มเหลวที่กำลังแก้ |
| --- | --- | --- |
| TCP แบบ plaintext | บังคับใช้ TLS 1.3 | รหัสผ่านและเนื้อไฟล์ถูกอ่านได้โดยใครก็ตามที่อยู่บนเส้นทาง |
| Username + password | รหัสจับคู่ 60 บิต พร้อมการพิสูจน์สองทาง | รหัสผ่านพิสูจน์ *ไคลเอนต์* ต่อ *เซิร์ฟเวอร์* แต่ไม่พิสูจน์อะไรกลับในทิศทางตรงข้าม |
| ไม่มีการพิสูจน์ตัวตนเซิร์ฟเวอร์ | ปักหมุด (pin) ลายนิ้วมือใบรับรอง และผูกไว้ *ภายใน* proof | การเข้ารหัสที่ไม่มีการพิสูจน์ตัวตน ป้องกันได้แค่ผู้ดักฟังเฉย ๆ ไม่ป้องกันผู้โจมตีเชิงรุก |
| อ่าน body ทั้งก้อนเข้าหน่วยความจำ | สตรีมทีละบล็อก 256 KiB | 1.0 ย้ายไฟล์ที่ใหญ่กว่า RAM ไม่ได้ |
| ใส่ชื่อไฟล์ดิบใน request line | percent-encode target | `GET my file.txt KUFT/1.0` ถูกแยกเป็น 4 token แล้วพัง |
| ตรวจ checksum ของ body อย่างเดียว | checksum **บวก** atomic rename **บวก** resume | การโอนที่ล้มเหลวสามารถทับไฟล์ดี ๆ ด้วยไฟล์ที่ไม่สมบูรณ์ได้ |

## 2. ระบบประกอบขึ้นอย่างไร

### 2.1 แผนผังโมดูล

```text
kuft.py                    จุดเข้าเพียงจุดเดียว กระจายไปยังคำสั่งย่อย
src/kuft/
    bootstrap.py           หา Python ที่มี `cryptography` ติดตั้งอยู่
    crypto.py              กุญแจ ใบรับรอง รหัสจับคู่ known hosts
    protocol.py            รูปแบบข้อมูลบนสาย: encode, decode, stream, status codes
    server.py              TLS listener, session state machine, request handlers
    client.py              การจับคู่ การปักหมุด การโอนย้าย และ shell แบบโต้ตอบ
    term.py                สี แถบความคืบหน้า ตาราง การรับ input แบบซ่อน
```

| โมดูล | บรรทัด | หน้าที่ | การตัดสินใจสำคัญภายใน |
| --- | ---: | --- | --- |
| `protocol.py` | 366 | รูปแบบข้อมูลบนสาย และเฉพาะรูปแบบข้อมูลบนสายเท่านั้น ไม่รู้จักไฟล์ socket TLS หรือผู้ใช้เลย | `Reader.pipe_body()` คำนวณ hash ไปพร้อมกับการสตรีม การตรวจสอบความถูกต้องจึงไม่ต้องอ่านข้อมูลซ้ำอีกรอบ |
| `crypto.py` | 379 | ตัวตนและความไว้วางใจ สร้างใบรับรอง PBKDF2 การสร้าง proof และ `known_hosts.json` | proof ใส่ length prefix และแยกด้วย label การเข้ารหัส input จึงเป็นแบบ injective |
| `server.py` | 693 | `Jail` (กักขอบเขต path), `RateLimiter`, `Session` (state machine), `serve()` (accept loop) | อัปโหลดลงไฟล์ชั่วคราวก่อน แล้วค่อย `os.replace` เข้าตำแหน่งจริงหลัง checksum ตรงเท่านั้น |
| `client.py` | 722 | นโยบายการปักหมุด `download()`/`upload()` และ `Shell` | ลายนิ้วมือที่เปลี่ยนไปจะโยน `FingerprintChanged` แล้วหยุด จงใจไม่มี prompt ให้กดผ่าน |
| `term.py` | 360 | ทุกไบต์ที่แสดงต่อผู้ใช้ | มีที่เดียวที่ต้องรองรับ `--no-color` และ `NO_COLOR` |
| `bootstrap.py` | 287 | รีสตาร์ตเข้าสู่ Python ที่ `import cryptography` ได้ | เป็นปัญหาสภาพแวดล้อมที่ผู้ใช้ไม่ควรต้องมานั่งแก้เอง |

**`protocol.py` ถูก import โดยทั้งสองฝั่ง** นี่คือการตัดสินใจเชิงโครงสร้างที่มี
ประโยชน์ที่สุดในโครงงาน: ไคลเอนต์กับเซิร์ฟเวอร์ไม่มีทางเข้าใจรูปแบบข้อมูลไม่ตรงกัน
ได้เลย เพราะมี encoder หนึ่งตัวและ decoder หนึ่งตัวเท่านั้นทั้งโปรเจกต์ ถ้าแก้ framing
ทั้งสองฝั่งจะพังพร้อมกันทันทีในชุดทดสอบ

### 2.2 โมเดลการทำงานพร้อมกัน (Concurrency)

```text
                   main thread
                        |
              listener.accept()  (timeout 0.5 วินาที วนถาม)
                        |
             semaphore: ยังมีช่องว่างใน 8 ช่องไหม?
               /                    \
             ไม่มี                    มี
              |                        |
        TLS handshake,           สร้าง worker thread
        ตอบ 503, ปิด                    |
                                  TLS 1.3 handshake
                                         |
                                  Session(...).run()
                                         |
                                    คืนช่องว่าง
```

* **หนึ่ง thread ต่อหนึ่ง connection** ซึ่งเหมาะกับงานนี้: session มีอายุยาว มีสถานะ
  และถูกครอบงำด้วย blocking I/O บน socket และไฟล์ การใช้ event loop ไม่ได้ประโยชน์
  อะไรที่ 8 ไคลเอนต์พร้อมกัน แต่แลกมาด้วยความซับซ้อนของโค้ดอย่างมาก
* **`threading.Semaphore` จำกัดจำนวนพร้อมกัน** ที่ `--max-clients` (ค่าเริ่มต้น 8)
  ไคลเอนต์ที่ 9 จะถูกปฏิเสธด้วย `503 SERVICE UNAVAILABLE` — และคำปฏิเสธนั้นถูกส่ง
  *ภายใน TLS* จึงเป็นการตอบตามโปรโตคอลจริง ไม่ใช่การตัดการเชื่อมต่อทิ้งเฉย ๆ
* **`RateLimiter` ต่อ connection** (fixed window ปิดไว้เป็นค่าเริ่มต้น) ตอบ
  `429 TOO MANY REQUESTS` พร้อมเฮดเดอร์ `retry-after`
* **socket มี timeout 300 วินาที** ไคลเอนต์ที่หายไปกลางคันจึงคืนช่องว่างให้ระบบ
  แทนที่จะยึดไว้ตลอดไป
* **accept loop ใช้การวนถามด้วย timeout 0.5 วินาที แทนการบล็อก** นี่เป็นการแก้ปัญหา
  เฉพาะของ Windows ที่ควรกล่าวถึง: Windows ไม่ขัดจังหวะ blocking socket call เมื่อกด
  Ctrl+C — ตัว console handler เพียงตั้งค่าธง และธงนั้นจะกลายเป็น `KeyboardInterrupt`
  ก็ต่อเมื่อ interpreter ได้รัน bytecode ครั้งถัดไป ถ้าจอดอยู่ใน `accept()` ตลอดกาล
  เหตุการณ์นั้นจะไม่เกิดขึ้นเลย เซิร์ฟเวอร์ก็จะเพิกเฉยต่อ Ctrl+C จนกว่าจะมีไคลเอนต์
  บังเอิญเชื่อมต่อเข้ามา

## 3. Service model ของชั้น Transport — เลือกอะไร และทำไม

นี่คือการตัดสินใจหลักด้านเครือข่ายของโครงงาน จึงขอให้เหตุผลอย่างเต็มรูปแบบ

### 3.1 แอปพลิเคชันนี้ต้องการอะไรจากชั้น Transport จริง ๆ

ก่อนจะเลือก ต้องระบุความต้องการในรูปของ **คุณสมบัติ** ไม่ใช่ในรูปของชื่อโปรโตคอล:

| # | ความต้องการ | ทำไมการรับส่งไฟล์จึงต้องการ |
| --- | --- | --- |
| R1 | **ข้อมูลต้องไม่สูญหาย** | ไฟล์ที่ขาดไปหนึ่งไบต์ ไม่ใช่ไฟล์ที่แย่ลงนิดหน่อย แต่คือไฟล์เสีย |
| R2 | **ส่งถึงตามลำดับ** | ไบต์ที่ 5,000,001 ต้องถูกเขียนหลังไบต์ที่ 5,000,000 ไม่งั้นไฟล์เละ |
| R3 | **ไม่ซ้ำ** | บล็อกที่ส่งซ้ำแล้วถูกเขียนสองครั้ง จะเลื่อนทุกอย่างหลังจากนั้นทั้งหมด |
| R4 | **Flow control** | เครื่องที่อ่านจาก SSD ผลิตข้อมูลได้เร็วกว่าที่แล็ปท็อปซึ่งเขียนลงดิสก์ช้า ๆ จะรับไหว ต้องมีกลไกดันกลับ |
| R5 | **Congestion control** | การอัดข้อมูลเต็มลิงก์ที่ใช้ร่วมกันโดยไม่ยอมถอย เป็นการเอาเปรียบผู้อื่น และในระดับใหญ่ทำให้เกิด congestion collapse |
| R6 | **ความหมายของ connection** | session ของเรามีสถานะ — ทักทายแล้ว, พิสูจน์ตัวตนแล้ว, พร้อมทำงาน ทั้งสองฝั่งต้องเห็นตรงกันว่ามี connection อยู่ และจบเมื่อไร |
| R7 | **ความลับและการพิสูจน์ตัวตนคู่สนทนา** | แบบจำลองภัยคุกคามคือเครื่องอื่นบน Wi-Fi เดียวกัน |
| R8 | **ความถูกต้องแบบ end-to-end** | ไฟล์ที่ลงจอดต้องพิสูจน์ได้ว่าเป็นไฟล์เดียวกับที่ส่งมา |

**สิ่งที่ไม่ต้องการ:** latency ที่มีขอบเขตแน่นอน, throughput ขั้นต่ำที่รับประกัน หรือ
กำหนดเวลาส่งถึงที่ตายตัว ข้อสังเกตนี้กลายเป็นจุดชี้ขาด — ดู §3.6

### 3.2 Service model สองแบบที่มีให้เลือก

| คุณสมบัติ | **TCP** | **UDP** |
| --- | --- | --- |
| การสร้าง connection | มี — three-way handshake และการปิดอย่างชัดเจน | ไม่มี แต่ละ datagram เป็นอิสระ |
| การรับประกันการส่งถึง | เชื่อถือได้: ACK, timeout, retransmission | Best-effort อาจสูญหาย |
| ลำดับ | รับประกัน ด้วย sequence number | ไม่มี อาจสลับลำดับ |
| การตัดข้อมูลซ้ำ | มี | ไม่มี |
| นามธรรมที่ให้ | **สตรีมไบต์ที่เชื่อถือได้** แบบ full-duplex | **ข้อความ (datagram)** ที่ไม่เชื่อถือได้ |
| Flow control | มี — receive window | ไม่มี |
| Congestion control | มี — AIMD, slow start | ไม่มี |
| ขนาดเฮดเดอร์ | 20 ไบต์ | 8 ไบต์ |
| รับประกันเวลา / throughput | **ไม่มี** | **ไม่มี** |
| ความปลอดภัย | **ไม่มี** | **ไม่มี** |

### 3.3 การเลือก: TCP, `AF_INET` + `SOCK_STREAM`, พอร์ตเริ่มต้น 5150

```python
listener = socket.socket(socket.AF_INET, socket.SOCK_STREAM)   # server.py
listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
listener.bind((cfg.host, cfg.port))
listener.listen(16)
```

จับคู่ความต้องการเข้ากับสิ่งที่ TCP ให้:

| ความต้องการ | สิ่งที่ตอบสนอง | ต้นทุนถ้าเลือก UDP |
| --- | --- | --- |
| R1 ไม่สูญหาย | TCP retransmission เมื่อ ACK timeout / duplicate ACK | ต้องเขียน sequence number, ACK, retransmission timer, การประมาณ RTT เอง |
| R2 ตามลำดับ | TCP sequence number และการประกอบใหม่ฝั่งรับ | ต้องเขียน reorder buffer เอง |
| R3 ไม่ซ้ำ | TCP sequence number | ต้องเขียนการตรวจจับข้อมูลซ้ำเอง |
| R4 flow control | TCP receive window (`rwnd`) | ต้องเขียน windowing และการประกาศ window เอง |
| R5 congestion control | TCP AIMD, slow start, fast recovery | ต้องเขียน congestion window และนโยบายถอยเอง |
| R6 ความหมาย connection | TCP three-way handshake และการปิดด้วย FIN | ต้องเขียนการสร้าง session และ timeout เอง |

คอลัมน์ขวามือคือข้อโต้แย้งทั้งหมดรวมอยู่ในที่เดียว: **การทำ R1–R6 บน UDP ก็คือการ
เขียน TCP ขึ้นมาใหม่** — และจะเป็นเวอร์ชันที่นักศึกษาคนเดียวเขียนในหนึ่งเทอม ไม่เคย
ผ่านการตรวจสอบ และรันบนเครือข่ายเดียวเท่านั้น ส่วนการ implement TCP ของจริงถูกโจมตี
และตรวจสอบมาตั้งแต่ปี 1981 และอยู่ใน kernel ซึ่งมองเห็น socket buffer และ timer
ได้อย่างถูกต้อง

### 3.4 เหตุผลชี้ขาดในทางปฏิบัติ: TLS

ความต้องการข้อ R7 ปิดประเด็นนี้อย่างสิ้นเชิง

* **TLS 1.3 ทำงานบน TCP** และถูกเปิดให้ใช้ผ่านโมดูล `ssl` ในไลบรารีมาตรฐานของ
  Python เป็นสแต็กที่ผ่านการตรวจสอบมาอย่างกว้างขวาง โค้ดเราเพียงแค่ตั้งค่ามัน:

  ```python
  ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
  ctx.minimum_version = ssl.TLSVersion.TLSv1_3    # ไม่เปิดช่องให้ต่อรองลดเวอร์ชัน
  ctx.load_cert_chain(certfile=..., keyfile=...)
  ctx.options |= ssl.OP_NO_COMPRESSION | ssl.OP_SINGLE_ECDH_USE
  ```

* **สิ่งที่เทียบเท่าบน UDP คือ DTLS** และโมดูล `ssl` ของ Python
  **ไม่เปิดให้ใช้งานเลย**

ดังนั้นการเลือก UDP จะบังคับให้เกิดผลลัพธ์อย่างใดอย่างหนึ่ง:

1. **เขียน record layer และ key exchange ขึ้นเอง** ซึ่งเป็นวิธีที่แน่นอนที่สุดในการ
   สร้างวิทยาการรหัสลับที่พัง เป็นความผิดพลาดที่วรรณกรรมด้านความปลอดภัยทั้งหมด
   เตือนไว้
2. **ปล่อยโปรแกรมโดยไม่มีการเข้ารหัส** ซึ่งก็คือ KUFT/1.0 — สิ่งที่เวอร์ชันนี้เกิดมา
   เพื่อแทนที่

ทั้งสองทางรับไม่ได้ TCP จึงไม่ใช่แค่ตัวเลือกที่ดีกว่า แต่เป็น **ตัวเลือกเดียว** ที่
สอดคล้องกับเป้าหมายข้อที่สองของโครงงาน

### 3.5 สิ่งที่ TCP *ไม่ได้* ให้ และสิ่งที่เราสร้างเสริมขึ้นมา

นี่คืออีกครึ่งหนึ่งของคำตอบที่ซื่อสัตย์ Service model ของ TCP ไม่สมบูรณ์สำหรับ
แอปพลิเคชันนี้จริง ๆ และช่องว่างแต่ละจุดถูกเติมอย่างจงใจที่ชั้น Application:

| ช่องว่างใน service model ของ TCP | ผลถ้าไม่สนใจ | คำตอบของ KUFT |
| --- | --- | --- |
| **สตรีมไบต์ไม่มีขอบเขตข้อความ** `send()` กับ `recv()` ไม่สอดคล้องกัน หนึ่ง `write()` อาจมาถึงเป็นสามการอ่าน หรือสาม write อาจมาถึงเป็นครั้งเดียว | ฝ่ายรับบอกไม่ได้ว่าข้อความหนึ่งจบตรงไหนและอันถัดไปเริ่มตรงไหน | **Framing ที่ชัดเจน** (§4.3): ส่วนหัวข้อความปิดท้ายด้วย CRLF และจบด้วยบรรทัดว่าง พร้อมบังคับใช้ `content-length` เมื่อมี body |
| **TCP checksum อ่อนแอและครอบคลุมแค่ทีละ hop** เป็นผลรวมแบบ one's-complement 16 บิต ออกแบบมาจับสัญญาณรบกวน คำนวณต่อ segment และ *ถูกคำนวณใหม่* โดยอุปกรณ์กลางทาง การแก้ไขของผู้โจมตีเชิงรุกจึงผ่านฉลุย และมันไม่บอกอะไรเลยเกี่ยวกับสิ่งที่ดิสก์ฝั่งรับเขียนลงไปจริง ๆ | ตรวจจับข้อมูลเสียได้บ้าง แต่ตรวจจับการดัดแปลงไม่ได้เลย | **SHA-256 แบบ end-to-end** ทั้งบนช่วงข้อมูลที่ส่ง *และ* บนไฟล์ที่ประกอบเสร็จ โดยคำนวณ hash ไปพร้อมกับข้อมูลที่ไหลผ่านใน `pipe_body()` นี่คือการใช้ end-to-end argument ตามตัวอักษร: การตรวจสอบเดียวที่มีความหมายคือการตรวจสอบที่ปลายทางทั้งสอง |
| **ไม่มีความลับ ไม่มีการพิสูจน์ตัวตนคู่สนทนา** | ทุกอย่างถูกอ่านและปลอมแปลงได้บน LAN | **บังคับ TLS 1.3 ขั้นต่ำ** บวกกับกลไกจับคู่ใน §4.7 ที่ผูกการพิสูจน์ตัวตนเข้ากับใบรับรอง |
| **ไม่มีสถานะระดับ session ของแอปพลิเคชัน** TCP รู้แค่ว่า "เชื่อมต่อแล้ว" แต่ไม่รู้ว่า "พิสูจน์ตัวตนแล้ว" | ใครก็ตามที่เชื่อมต่อได้ก็สั่ง `GET` ได้ | **State machine ของ session** (§4.6): ทุกคำสั่งยกเว้น `HELLO` และ `AUTH` ตอบ `401` จนกว่า proof จะผ่าน |
| **connection ที่ขาดทำให้เสียการโอนทั้งครั้ง** TCP กู้คืน segment ไม่ใช่ไฟล์ | ดาวน์โหลด 4 GB ที่ขาดตอนที่ 90% ต้องเริ่มใหม่จากศูนย์ | **การเริ่มต่อระดับแอปพลิเคชัน**: เก็บไฟล์ที่ยังไม่ครบไว้เป็น `.part` แล้ว `GET` พร้อมเฮดเดอร์ `range: N` จะส่งต่อจากตำแหน่งนั้น พร้อมตอบ `206` |
| **ไม่รับประกัน throughput หรือขอบเขต delay** | — | **ไม่จำเป็นต้องมี** ดูหัวข้อถัดไป |

### 3.6 ทำไมการที่ TCP ไม่รับประกันเรื่องเวลาจึงไม่เสียหายอะไรกับเรา

Service model ของ TCP จงใจไม่ให้ throughput ขั้นต่ำและไม่ให้ขอบเขต latency สำหรับ
แอปพลิเคชันหลายประเภทนั่นคือข้อจำกัดที่แท้จริง แต่สำหรับงานนี้มันไม่มีผลใด ๆ และ
เหตุผลควรพูดให้ตรง:

> **ในการรับส่งไฟล์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มาตรงเวลาทุกประการ**

ไม่มีอะไรถูกนำไปใช้จนกว่าไฟล์ทั้งไฟล์จะมาถึงและ hash ผ่านการตรวจสอบ การโอนที่หยุด
ชะงักไปสองวินาทีแล้วไปต่อ ให้ผลลัพธ์เหมือนกันทุกไบต์กับการโอนที่ไม่เคยสะดุด การที่
TCP ยอมแลก latency เพื่อความน่าเชื่อถือ — รอ retransmission หรือลด congestion window
ลงครึ่งหนึ่ง — จึงเป็นการแลกที่ KUFT ยินดีเสมอ

### 3.7 กรณีที่ UDP *จะ* เป็นคำตอบที่ถูกต้อง

การเลือกขึ้นอยู่กับบริบท ไม่ใช่คำตอบตายตัว UDP คือ transport ที่ถูกต้องเมื่อ datagram
ที่มาช้าถือว่า *ไร้ค่า* ไม่ใช่แค่ *ล่าช้า*:

* **เสียงและวิดีโอสด** — แพ็กเก็ตเสียงที่มาช้า 400 ms ไม่เหลือช่วงเวลาให้เล่นแล้ว
  การกลบช่องว่างดีกว่าการรอ retransmission
* **Telemetry และสถานะเกมแบบเรียลไทม์** — ข้อมูลอัปเดตชิ้นถัดไปแทนที่ชิ้นก่อนหน้า
  การส่งสถานะเก่าซ้ำมีแต่โทษ
* **การถาม-ตอบครั้งเดียวจบอย่าง DNS** — การทำ handshake แพงกว่าตัวคำถามเสียอีก
  ให้ลองใหม่ที่ชั้นแอปพลิเคชันแทน
* **Multicast** — TCP ทำ multicast ไม่ได้ แต่ UDP ทำได้

ไม่มีข้อใดตรงกับการย้ายไฟล์เลย ต้นทุนของ TCP (latency จาก handshake, head-of-line
blocking, สถานะต่อ connection) ล้วนเป็นต้นทุนที่ KUFT ยินดีจ่าย และการรับประกันของ
TCP ล้วนเป็นสิ่งที่ KUFT ต้องการจริง ๆ

### 3.8 แต่ละชั้นอยู่ตรงไหน

```text
  +------------------------------------------------------------+
  |  application  |  KUFT/2.0  — framing, methods, status codes,|
  |               |              pairing proof, SHA-256, resume |
  +------------------------------------------------------------+
  |  security     |  TLS 1.3   — ความลับ ความถูกต้อง             |
  |  (บน TCP)     |              AEAD, forward secrecy          |
  +------------------------------------------------------------+
  |  transport    |  TCP       — เชื่อถือได้ เรียงลำดับ สตรีมไบต์  |
  |               |              flow + congestion control      |
  |               |              พอร์ต 5150                      |
  +------------------------------------------------------------+
  |  network      |  IPv4      — ส่ง datagram แบบ best-effort    |
  +------------------------------------------------------------+
  |  link         |  Ethernet / 802.11                          |
  +------------------------------------------------------------+
```

อ่านจากล่างขึ้นบน: IP ให้ datagram แบบ best-effort; TCP แปลงมันเป็นสตรีมไบต์ที่
เชื่อถือได้และเรียงลำดับ; TLS แปลงสตรีมนั้นเป็นสตรีมที่เป็นความลับและพิสูจน์ตัวตนได้;
และ KUFT แปลง *สตรีมนั้น* เป็นข้อความที่แยกเป็นชิ้นและตรวจสอบได้ ซึ่งบรรทุกไฟล์ไป

## 4. ออกแบบโปรโตคอลอย่างไร

### 4.1 ข้อจำกัดที่การออกแบบต้องทำให้ได้

1. **ดีบักด้วยตาเปล่าได้** ส่วนควบคุมต้องอ่านออกในเทอร์มินัลหรือใน packet capture
   โดยไม่ต้องมีตัวถอดรหัส
2. **ไม่กำกวมกับ payload ใด ๆ** ไฟล์อาจมี CRLF, NUL หรือไบต์ใดก็ได้ Framing ต้อง
   ไม่ขึ้นกับ *เนื้อหา* ของ body เด็ดขาด
3. **ไม่กำกวมกับชื่อไฟล์ใด ๆ** ช่องว่างและอักษรไทยในชื่อไฟล์ต้องไม่ทำให้ parser สับสน
4. **สตรีมได้** ต้องไม่มีข้อความใดที่บังคับให้ต้องเก็บ payload ทั้งก้อนไว้ในหน่วยความจำ
5. **มีขอบเขต** ทุกความยาวที่คู่สนทนามีอิทธิพลต่อได้ ต้องมีเพดานตายตัว
6. **ขยายได้** การเพิ่มเฮดเดอร์ต้องไม่ทำให้ parser ของฝั่งเวอร์ชันเก่าพัง

### 4.2 รูปแบบ: ส่วนหัวเป็นข้อความ ตามด้วย body ไบนารีที่นับจำนวนไว้

```
message   = head CRLF [ body ]
head      = start-line CRLF *( header CRLF )
header    = field-name ":" OWS field-value
```

ตัวอย่างจริง:

```
GET /report.pdf KUFT/2.0\r\n          <- request line: 3 token ASCII
range: 0\r\n                          <- เฮดเดอร์ ไม่สนตัวพิมพ์เล็กใหญ่
\r\n                                  <- บรรทัดว่างปิดส่วนหัว
                                      <- GET request ไม่มี body

KUFT/2.0 200 OK\r\n                   <- status line
content-length: 8213\r\n              <- บังคับมีเมื่อมี body ตามมา
checksum: sha256=1f3a...\r\n
whole-checksum: sha256=1f3a...\r\n
detail: sending report.pdf\r\n
\r\n
<ข้อมูล 8213 ไบต์พอดี ไม่ตีความใด ๆ>
```

นี่คือรูปแบบของ HTTP และการหยิบยืมนี้เป็นความตั้งใจ: มันคือ framing ชั้นแอปพลิเคชัน
ที่ประสบความสำเร็จที่สุดเท่าที่เคยมีการใช้งานมา นักศึกษาเครือข่ายทุกคนอ่านออกอยู่แล้ว
และคุณสมบัติของมันเป็นที่เข้าใจกันดี สิ่งที่ KUFT **ไม่ได้** หยิบยืมคือความซับซ้อนที่
HTTP สะสมมา — ไม่มี chunked encoding ไม่มี content negotiation ไม่มี cookie ไม่มี
caching ไม่มี pipelining

**ทางเลือกที่พิจารณาแล้วตัดทิ้ง:**

| ทางเลือก | เหตุผลที่ไม่เลือก |
| --- | --- |
| Binary TLV (type-length-value) | กะทัดรัดและ parse เร็ว แต่มองไม่เห็นใน packet capture และดีบักยากมาก ส่วนควบคุมมีแค่ไม่กี่ข้อความต่อ session ไบต์ที่ประหยัดได้จึงไม่มีความหมายเมื่อเทียบกับ body ขนาดหลายกิกะไบต์ |
| ข้อความแบบ JSON | ต้องมี length prefix อยู่ดี หรือไม่ก็ต้อง parse แบบ incremental และบรรทุกข้อมูลไบนารีดิบไม่ได้ถ้าไม่ base64 ซึ่งเพิ่มขนาด 33% ในทุกไฟล์ |
| แบ่งด้วยตัวคั่นและ end marker | ต้องสแกนหา marker ใน body ซึ่งแปลว่าต้อง escape marker ภายใน body ซึ่งแปลว่า framing ขึ้นกับเนื้อหา ขัดกับข้อจำกัดข้อ 2 |

### 4.3 การตัดสินใจสี่ข้อเรื่อง framing

**(ก) ส่วนหัวเป็น US-ASCII และจบที่บรรทัดว่างแรก** ผลที่ตามมาคือ parser ไม่เคย
ตรวจสอบ body เลย ดังนั้น body จึงมี CRLF, NUL หรือไบต์อะไรก็ได้ โดยไม่ต้อง escape
และไม่มีต้นทุนใด ๆ

**(ข) `content-length` บังคับมีเสมอเมื่อมี body ตามมา** ฝ่ายรับจึงรู้ *แน่นอน* ว่าต้อง
อ่านกี่ไบต์ และไม่ต้องเดาว่าข้อความจบตรงไหน นี่คือสิ่งที่ทำให้ส่งข้อความติด ๆ กันบน
connection เดียวได้อย่างปลอดภัย และเป็นสิ่งที่ทำให้สตรีมได้: `pipe_body()` อ่านตาม
จำนวนที่รู้แล้วทีละบล็อก 256 KiB ตรงเข้าไฟล์ปลายทาง คำนวณ hash ไปด้วย โดยใช้
หน่วยความจำคงที่ ไม่ว่าไฟล์จะขนาด 4 KB หรือ 40 GB

**(ค) target ใน request line ถูก percent-encode**

```python
TARGET_SAFE = "/*-._~"
def encode_target(target): return quote(target, safe=TARGET_SAFE, encoding="utf-8")
```

ทุกอย่างที่อยู่นอก `A-Z a-z 0-9 / * - . _ ~` จะกลายเป็น `%XX` ตามไบต์ UTF-8 ของมัน
สิ่งนี้รับประกันว่า request line จะมี *สาม token คั่นด้วยช่องว่างเสมอ* ไม่ว่าไฟล์จะชื่ออะไร:

```
GET /Quarterly%20Report%20(final).pdf KUFT/2.0
PUT /%E0%B8%A3%E0%B8%B2%E0%B8%A2%E0%B8%87%E0%B8%B2%E0%B8%99.txt KUFT/2.0
```

ถ้าไม่มีสิ่งนี้ `GET Quarterly Report (final).pdf KUFT/2.0` จะถูกแยกเป็นห้า token และ
parse ไม่ผ่าน — ซึ่งเป็นจุดที่ KUFT/1.0 พังพอดี

**(ง) ทุกความยาวที่คู่สนทนามีอิทธิพลต่อได้ มีเพดานตายตัว**

| ขีดจำกัด | ค่า | บังคับใช้ด้วย |
| --- | --- | --- |
| บรรทัดควบคุม | 8 KiB | `400` |
| จำนวนเฮดเดอร์ต่อข้อความ | 64 | `400` |
| Control body (listing, proof) | 4 MiB | `413` |
| Body ของการอัปโหลด | `--max-upload` ค่าเริ่มต้น 8 GiB | `413` |
| ขนาดบล็อกการโอน | 256 KiB | — |

คู่สนทนาที่ส่งบรรทัดเฮดเดอร์โดยไม่มี CRLF จะทำให้เซิร์ฟเวอร์จองหน่วยความจำไม่จำกัด
ไม่ได้ เพราะ `readline(MAX_LINE + 1)` หยุดมันไว้

มีอีกกฎหนึ่งที่ปิดช่องโหว่จริง: **ตัว encoder ปฏิเสธที่จะส่งค่าเฮดเดอร์ที่มี CR หรือ LF**

```python
if "\r" in text or "\n" in text:
    raise ValueError(f"header {name!r} contains a line break")
```

ถ้าไม่มีข้อนี้ ชื่อไฟล์ที่มี `\r\n` อยู่ข้างในสามารถแทรกเฮดเดอร์ปลอม — หรือแทรก
*status line* ปลอม — เข้าไปในคำตอบได้ การปฏิเสธตั้งแต่ตอน encode หมายความว่า
ไม่มีผู้เรียกใช้รายใดเปิดช่องโหว่นี้ได้เลย

### 4.4 ชุดคำสั่ง (Methods)

เก้าคำสั่ง เลือกให้แต่ละคำสั่งจับคู่กับปฏิบัติการบนระบบไฟล์หนึ่งอย่างพอดี และไม่มี
คำสั่งใดครอบคลุมคำสั่งอื่น:

| Method | Target | Body | จุดประสงค์ |
| --- | --- | --- | --- |
| `HELLO` | `*` | — | ตกลงความสามารถ รับ salt และ server nonce |
| `AUTH` | `*` | — | พิสูจน์ว่ารู้รหัสจับคู่ และรับ proof จากเซิร์ฟเวอร์ |
| `LIST` | ไดเรกทอรี | — | รายการไฟล์ในรูปแถวคั่นด้วย tab |
| `STAT` | ไฟล์ | — | ขนาด เวลาแก้ไข checksum โดยไม่โอนข้อมูล |
| `GET` | ไฟล์ | — | ดาวน์โหลด; `range: N` ขอเฉพาะส่วนท้าย |
| `PUT` | ไฟล์ | payload | อัปโหลด; ปรับพฤติกรรมด้วย `overwrite`, `range` |
| `DELETE` | path | — | ลบไฟล์หรือไดเรกทอรีว่าง |
| `MKDIR` | ไดเรกทอรี | — | สร้างไดเรกทอรี |
| `MOVE` | path | — | เปลี่ยนชื่อ/ย้าย; เฮดเดอร์ `destination` ระบุปลายทาง |
| `QUIT` | `*` | — | ปิดการเชื่อมต่ออย่างสุภาพ |

สิ่งที่จงใจไม่มี: ไม่มี `COPY` (ใช้ `get` + `put` ฝั่งไคลเอนต์), ไม่มี `APPEND`
(ใช้ `PUT` พร้อม `range`), ไม่มี `CHMOD` (สิทธิ์ไม่อยู่ในแบบจำลอง) และไม่มี `DELETE`
แบบวนลึก (ไดเรกทอรีที่ไม่ว่างจะได้ `409` — การลบแบบวนลึกควรเป็นลูปฝั่งไคลเอนต์ที่
ผู้ใช้มองเห็น)

`STAT` มีคุณค่าตรงที่มันทำให้การปฏิเสธ `put` มีต้นทุนต่ำ: ไคลเอนต์ถามก่อน อัปโหลด
ขนาด 40 GB จึงไม่ถูกส่งขึ้นลิงก์ช้า ๆ เพื่อมาโดนปฏิเสธด้วย `409` ตอนจบ

### 4.5 Status codes

ใช้รหัสสามหลักตามคลาสของ HTTP เพื่อให้ *คลาส* มีความหมายแม้ผู้รับจะไม่รู้จักรหัส
เฉพาะตัวนั้น — `2xx` สำเร็จ, `4xx` เป็นความผิดของไคลเอนต์, `5xx` เป็นความผิดของ
เซิร์ฟเวอร์

| | |
| --- | --- |
| **2xx** | `200 OK` · `201 CREATED` · `204 NO CONTENT` · `206 PARTIAL CONTENT` |
| **4xx** | `400 BAD REQUEST` · `401 UNAUTHORIZED` · `403 FORBIDDEN` · `404 NOT FOUND` · `405 METHOD NOT ALLOWED` · `409 CONFLICT` · `413 PAYLOAD TOO LARGE` · `416 RANGE NOT SATISFIABLE` · **`422 CHECKSUM MISMATCH`** · `429 TOO MANY REQUESTS` |
| **5xx** | `500 INTERNAL ERROR` · `503 SERVICE UNAVAILABLE` · `505 VERSION NOT SUPPORTED` |

`422` คือรหัสเดียวที่เป็นของ KUFT โดยแท้ ความหมายคือ *คำขอถูกต้องตามรูปแบบ และ
ข้อมูลมาถึงครบตามที่ชั้น transport รับรู้ แต่ payload ไม่ตรงกับ checksum ที่ผู้ส่ง
ประกาศไว้* ไม่มีรหัส HTTP ใดหมายความแบบนั้น และนี่คือความล้มเหลวที่สำคัญที่สุดที่
โปรโตคอลนี้ต้องรายงานได้

ทุกคำตอบมีเฮดเดอร์ `detail` ที่อธิบายเป็นภาษามนุษย์ และทั้งสองโปรแกรมพิมพ์รหัส
วลี และ detail ในทุกการแลกเปลี่ยน การดีบักโปรโตคอลเครือข่ายโดยไม่มีสิ่งนี้ยากเกิน
ความจำเป็น

### 4.6 State machine ของ session

```text
                 TCP connect
                      |
             TLS 1.3 handshake
                      |
                      v
                [ connected ] -- อะไรก็ตามที่ไม่ใช่ HELLO/AUTH --> 401
                      |  HELLO
                      v
                 [ greeted ] -- อะไรก็ตามที่ไม่ใช่ AUTH --> 401
                      |  AUTH ด้วย proof ที่ถูกต้อง
                      v
            +--> [ authenticated ]
            |         |
   LIST STAT|         |  QUIT
   GET  PUT |         v
   DELETE   |    [ closed ]
   MKDIR    |
   MOVE ----+
```

กฎสามข้อที่ทำให้ state machine นี้ปลอดภัย:

* **`AUTH` ก่อน `HELLO` ได้ `400` ไม่ใช่ `401`** เพราะยังไม่มี server nonce `Ns`
  จึงไม่มีอะไรให้ proof ผูกเข้ากับ มันคือความผิดพลาดของ framing ไม่ใช่ความล้มเหลว
  ของการอนุญาต และการบอกให้ตรงช่วยคนที่กำลังดีบัก
* **ความผิดพลาดของ framing (`400`) จะปิด connection** เมื่อสตรีมหลุดจังหวะแล้ว
  ไม่มีวิธีใดที่จะหาขอบเขตข้อความถัดไปได้อย่างน่าเชื่อถือ — การพยายามหาจังหวะใหม่
  คือช่องทางที่ parser ถูกเจาะ
* **คำขอที่ถูกปฏิเสธก็ยังต้องอ่าน body ทิ้ง** (`_discard_body`) การปฏิเสธด้วย `409`
  ที่ทิ้งข้อมูลอัปโหลด 40 GB ค้างอยู่ในสตรีมจะทำให้คำขอถัดไปหลุดจังหวะ Framing ที่
  ถูกต้องหมายถึงต้องระบายสิ่งที่เราปฏิเสธออกไปด้วย

### 4.7 กลไกจับคู่ (Pairing) — หัวใจของการออกแบบ

**ปัญหา** TLS ให้ช่องทางที่เป็นความลับ แต่ใบรับรองของเซิร์ฟเวอร์เป็นแบบ self-signed
บนเครือข่ายที่มีแค่แล็ปท็อปสองเครื่องไม่มี certificate authority ให้อ้างอิง ใบรับรอง
เพียงลำพังจึงไม่พิสูจน์อะไรเลย: ผู้โจมตีสร้างขึ้นเองได้ง่ายพอ ๆ กัน และการเข้ารหัส
ไปหาคู่สนทนาที่ไม่รู้ว่าเป็นใครนั้นแทบไม่มีค่า

**แนวคิดหลัก** ผูก proof ของการพิสูจน์ตัวตนเข้ากับ *ใบรับรองที่ถูกนำเสนอจริง* แล้ว
คนกลางจะส่งต่อ proof ไม่ได้

**ค่าที่ใช้:**

| สัญลักษณ์ | นิยาม |
| --- | --- |
| `code` | อักขระ base32 ตาม RFC 4648 จำนวน 12 ตัว — **60 บิต** แสดงเป็น `XXXX-XXXX-XXXX` |
| `salt` | 16 ไบต์สุ่ม สร้างครั้งเดียวต่อเซิร์ฟเวอร์และเก็บไว้ |
| `K` | `PBKDF2-HMAC-SHA256(code, salt, 200000, 32)` |
| `FP` | `SHA-256(DER(ใบรับรองเซิร์ฟเวอร์))` — ลายนิ้วมือ |
| `Nc`, `Ns` | ฝ่ายละ 32 ไบต์สุ่ม **สร้างใหม่ทุก connection** |

**การสร้าง proof** โดยให้ `L(x)` คือความยาวของ `x` ในรูป big-endian 4 ไบต์:

```
proof(label) = HMAC-SHA256( K,
                 L(label) || label ||
                 L(FP)    || FP    ||
                 L(Nc)    || Nc    ||
                 L(Ns)    || Ns    )

ไคลเอนต์: label = "KUFT/2.0 client-proof"
เซิร์ฟเวอร์: label = "KUFT/2.0 server-proof"
```

**ลำดับการแลกเปลี่ยน:**

```
C -> S   HELLO * KUFT/2.0

S -> C   KUFT/2.0 200 OK
         salt:  <base64>          salt ที่เซิร์ฟเวอร์เก็บไว้
         nonce: <base64 Ns>       nonce ใหม่ของเซิร์ฟเวอร์
         auth:  pairing-code

C -> S   AUTH * KUFT/2.0
         nonce: <base64 Nc>       nonce ใหม่ของไคลเอนต์
         proof: <base64 proof("KUFT/2.0 client-proof")>

S -> C   KUFT/2.0 200 OK
         proof: <base64 proof("KUFT/2.0 server-proof")>
```

**ทำไมแต่ละองค์ประกอบจึงอยู่ตรงนั้น:**

| องค์ประกอบ | ป้องกันอะไร |
| --- | --- |
| `FP` อยู่ภายใน MAC | **การดักกลางทาง (machine-in-the-middle)** ดูคำอธิบายด้านล่าง นี่คือจุดที่รับน้ำหนักทั้งหมด |
| `Nc` และ `Ns` ที่สร้างใหม่ทุกครั้ง | **Replay** proof ที่ถูกดักไว้ใช้ได้กับ connection เดียวเท่านั้น และไม่มีวันใช้ได้อีก |
| label สองอันที่ต่างกัน | **Reflection** proof ของไคลเอนต์ถูกส่งย้อนกลับเป็น proof ของเซิร์ฟเวอร์ไม่ได้ เพราะ label ต่างกัน MAC จึงต่างกัน |
| Length prefix | **ความกำกวมในการเข้ารหัส** ทำให้การเข้ารหัส input เป็นแบบ injective ไม่มี `(label, FP, Nc, Ns)` สองชุดที่ต่างกันจะให้สตริงไบต์เดียวกันเข้าไปคำนวณ MAC |
| PBKDF2 200,000 รอบ | **การเดาแบบ offline** proof ที่ถูกดักได้ให้แค่การโจมตี offline ต่อ 60 บิตที่มี PBKDF2 200,000 รอบขวางอยู่ |
| `hmac.compare_digest` | **Timing side channel** เปรียบเทียบด้วยเวลาคงที่ ทำทั้งสองฝั่ง |
| หน่วง 1 วินาทีเมื่อล้มเหลว | **การเดารหัสแบบ online** โดยไม่บล็อกส่วนที่เหลือของเซิร์ฟเวอร์ |
| ชุดอักขระ base32 (ไม่มี `0 1 8 9`) | **ความผิดพลาดในการอ่าน/พิมพ์ของมนุษย์** `O`/`0` และ `I`/`1` สับสนกันไม่ได้ และตัวที่พิมพ์ผิดจะถูกซ่อมให้อัตโนมัติ |

**ทำไมลายนิ้วมือจึงเป็นชิ้นส่วนที่รับน้ำหนัก** สมมติผู้โจมตีแทรกอยู่ระหว่างสองเครื่อง
ปิด TLS ทั้งสองด้านด้วยใบรับรองของตัวเอง ลายนิ้วมือ `FP'`:

```
   ไคลเอนต์  <--TLS(FP')-->  ผู้โจมตี  <--TLS(FP)-->  เซิร์ฟเวอร์
```

ไคลเอนต์คำนวณ proof ของตัวเองบน `FP'` เพราะนั่นคือใบรับรองที่มันเห็น ผู้โจมตีส่ง
proof นั้นต่อไปโดยไม่แก้ไข — มันคำนวณใหม่ไม่ได้ เพราะการคำนวณใหม่ต้องใช้ `K`
เซิร์ฟเวอร์ตรวจ proof เทียบกับ `FP` ซึ่งเป็นลายนิ้วมือของตัวเอง `FP ≠ FP'` MAC จึง
ต่างกัน และเซิร์ฟเวอร์ตอบ `401`

ผู้โจมตีซ่อมสถานการณ์นี้ไม่ได้ถ้าไม่มี `K` และหา `K` ไม่ได้ถ้าไม่มีรหัสจับคู่ —
**ซึ่งไม่เคยวิ่งผ่านเครือข่ายในรูปแบบใดเลย** ไม่ว่าจะเข้ารหัสหรือไม่ก็ตาม

**การปักหมุด (Pinning) และ prompt ที่หายไป** เมื่อการแลกเปลี่ยนสำเร็จครั้งแรก
ไคลเอนต์เก็บ `FP` และ `K` ผูกกับ `host:port` ไว้ใน `known_hosts.json` การเชื่อมต่อ
ครั้งต่อ ๆ ไปจึงข้ามการถามรหัสไปเลย และถ้า `FP` ที่เก็บไว้ไม่ตรงกับที่ถูกนำเสนอ
ไคลเอนต์จะ **หยุดทันที**:

```python
if record and not hmac.compare_digest(record.fingerprint, self.fingerprint):
    raise FingerprintChanged(...)
```

จงใจ **ไม่มี prompt ถามว่า "จะเชื่อมต่อต่อไปไหม"** ลายนิ้วมือที่เปลี่ยนบนโฮสต์ที่
ปักหมุดไว้แล้ว หมายถึงอย่างใดอย่างหนึ่ง: เซิร์ฟเวอร์ถูกสร้างใหม่ — ซึ่งผู้ใช้ยืนยันได้
ผ่านช่องทางอื่นแล้วเคลียร์ด้วย `kuft.py forget <host>` — หรือการเชื่อมต่อกำลังถูกดัก
และ **กล่องข้อความให้กดยืนยันคือวิธีที่คนกดผ่านกรณีหลังพอดี** การออกแบบจึงปฏิเสธ
ที่จะเสนอมัน การกู้คืนต้องใช้คำสั่งแยกต่างหากอย่างตั้งใจ

### 4.8 ความหมายของการโอนย้าย

**ดาวน์โหลด** `GET` ตอบกลับพร้อม `size`, `checksum` (ของช่วงข้อมูลที่ส่ง) และ
`whole-checksum` (ของไฟล์ทั้งไฟล์) แล้วตามด้วย body ไคลเอนต์คำนวณ hash ขณะเขียน
ลง `name.part` และเทียบกับ `checksum`; เมื่อผ่านแล้วจึง hash ไฟล์ที่ประกอบเสร็จและ
เทียบกับ `whole-checksum` **ทั้งสองต้องผ่าน** ก่อนที่ `os.replace(partial, destination)`
จะเปลี่ยนชื่อเป็นชื่อจริง ถ้าล้มเหลว ไฟล์ `.part` จะยังอยู่ — ซึ่งเป็นสิ่งที่ทำให้ครั้งถัดไป
ทำต่อได้แทนที่จะเริ่มใหม่

**อัปโหลด** `PUT` ส่ง `checksum` มาด้วย และอาจมี `overwrite: true` เซิร์ฟเวอร์เขียน
body ลงไฟล์ชั่วคราว *ในไดเรกทอรีปลายทาง* คำนวณ hash เปรียบเทียบ แล้วจึงเปลี่ยนชื่อ:

```python
fd, temp_name = tempfile.mkstemp(dir=str(path.parent), prefix=".kuft-", suffix=".part")
...
written, digest = self.reader.pipe_body(request.headers, handle)
if claimed and claimed != digest:
    temp_path.unlink(missing_ok=True)
    raise ProtocolError(..., 422)
os.replace(temp_path, path)
```

มีสองรายละเอียดที่สำคัญ ไฟล์ชั่วคราวอยู่ใน **ไดเรกทอรีเดียวกัน** เพื่อให้ `os.replace`
เป็นการเปลี่ยนชื่อภายในระบบไฟล์เดียวกัน ซึ่งเป็นปฏิบัติการแบบ atomic และการเปลี่ยนชื่อ
เกิดขึ้น **หลังจาก** checksum ตรงเท่านั้น การอัปโหลดที่ขาดตอนหรือถูกดัดแปลงจึงไม่มีทาง
ทิ้งไฟล์ที่ไม่สมบูรณ์ไว้ภายใต้ชื่อจริงได้ — ไฟล์เวอร์ชันเดิมรอดโดยไม่ถูกแตะต้อง

**การทำต่อ (Resume)** `GET` พร้อม `range: N` จะ seek ไปที่ `N` แล้วตอบ `206` โดย
`checksum` ครอบคลุมเฉพาะไบต์ตั้งแต่ `N` เป็นต้นไป ส่วน `PUT` พร้อม `range: N` จะ
เขียนต่อจากตำแหน่ง `N` แต่ต่อเมื่อขนาดไฟล์ปัจจุบันบนเซิร์ฟเวอร์เท่ากับ `N` *พอดี*
ไม่เช่นนั้นตอบ `416` เพราะการเขียนต่อผิดตำแหน่งจะสร้างไฟล์เสียแบบเงียบ ๆ

### 4.9 การกักขอบเขต (Jail)

ทุก target ถูก resolve เทียบกับ share root แล้วจึงตรวจสอบ:

```python
candidate = (self.root / cleaned.lstrip("/")).resolve()
if candidate != self.root and self.root not in candidate.parents:
    raise ProtocolError("path escapes the shared directory", 403)
```

`resolve()` ยุบ `..` **และตาม symlink ก่อนการตรวจสอบ** ดังนั้น symlink ที่ชี้ออกนอก
share จึงถูกปฏิเสธเหมือนกับ `../` ตรง ๆ — ซึ่งเป็นสิ่งที่การตรวจแบบเทียบ prefix ของ
สตริงจะพลาด backslash ถูกแปลงเป็น forward slash เพื่อไม่ให้ path สไตล์ Windows
เล็ดลอด และ NUL ใน path ได้ `400`

การพยายามหลุดขอบเขตตอบ `403` ไม่เคยตอบ `404` และคำตอบไม่เคยเปิดเผยว่า path
ภายนอกนั้นมีอยู่จริงหรือไม่ ตัว share root เองก็ลบไม่ได้

## 5. พฤติกรรมเมื่อล้มเหลว

โปรโตคอลถูกนิยามด้วยวิธีที่มันล้มเหลว ไม่น้อยไปกว่าวิธีที่มันสำเร็จ:

| สถานการณ์ | คำตอบ | ผลต่อข้อมูล |
| --- | --- | --- |
| รหัสจับคู่ผิด | `401` หลังหน่วง 1 วินาที session ยังเปิดอยู่ให้พิมพ์ใหม่ได้ | ไม่เปิดเผยอะไร |
| ใบรับรองเซิร์ฟเวอร์เปลี่ยน | ไคลเอนต์หยุดก่อนส่งอะไรทั้งสิ้น | ไม่มีการเชื่อมต่อ |
| checksum อัปโหลดไม่ตรง | `422` ลบไฟล์ชั่วคราวทิ้ง | ไฟล์เดิมไม่ถูกแตะ |
| checksum ดาวน์โหลดไม่ตรง | ไคลเอนต์แจ้งข้อผิดพลาด เก็บ `.part` ไว้ | ไม่มีไฟล์เสียเกิดขึ้น |
| การโอนถูกขัดจังหวะ | connection ปิด | เก็บ `.part` ไว้ `get` ครั้งถัดไปทำต่อได้ |
| `../` หรือ symlink หลุดขอบเขต | `403` | ไม่มีอะไรนอก share ที่เข้าถึงหรือถูกเปิดเผยได้ |
| อัปโหลดทับไฟล์เดิมโดยไม่ใส่ `--force` | `409` ปฏิเสธ *ก่อน* ส่ง body | ไฟล์เดิมไม่ถูกแตะ |
| body ใหญ่กว่า `--max-upload` | `413` ระบาย body ทิ้งเพื่อรักษาจังหวะสตรีม | ไม่มีการเขียนใด ๆ |
| คำขอถี่เกินไป | `429` + `retry-after` | session ยังอยู่ |
| ไคลเอนต์รายที่ 9 พร้อมกัน | `503` ส่งภายใน TLS | ปฏิเสธอย่างเรียบร้อย |
| framing ผิดรูป | `400` + `connection: close` | ทิ้งสตรีมไป ไม่พยายามหาจังหวะใหม่ |
| เวอร์ชันโปรโตคอลผิด | `505` | — |

## 6. ตั้งแต่ต้นจนจบ: `get` หนึ่งครั้ง ทีละขั้น

```
 1.  ไคลเอนต์: socket.create_connection((host, 5150))
               -> TCP three-way handshake

 2.  ทั้งคู่:   TLS 1.3 handshake  (minimum_version = TLSv1_3 ไม่ยอมลดเวอร์ชัน)
               ไคลเอนต์คำนวณ SHA-256 บนใบรับรองรูปแบบ DER  ->  FP

 3.  ไคลเอนต์: ค้น known_hosts ด้วยคีย์ "host:5150"
               ไม่พบ -> ถามรหัส แล้วคำนวณ K = PBKDF2(code, salt, 200k)
               พบ    -> ใช้ K ที่เก็บไว้; ถ้า FP ที่เก็บไว้ไม่ตรง ให้หยุดทันที

 4.  C -> S: HELLO * KUFT/2.0
     S -> C: 200 OK   salt, nonce=Ns, methods, tls, read-only, max-upload

 5.  C -> S: AUTH * KUFT/2.0   nonce=Nc, proof=HMAC(K, label|FP|Nc|Ns)
     S -> C: 200 OK   proof=HMAC(K, server-label|FP|Nc|Ns)
             เซิร์ฟเวอร์ใช้ compare_digest; ไคลเอนต์ตรวจคำตอบด้วยวิธีเดียวกัน
             ครั้งแรก: ไคลเอนต์ปักหมุด {FP, K} ลง known_hosts.json

 6.  C -> S: LIST / KUFT/2.0
     S -> C: 200 OK   content-length: 214
             FILE<TAB>8213<TAB>2026-08-26T09:11:04Z<TAB>report.pdf   ...

 7.  C -> S: GET /report.pdf KUFT/2.0        (+ range: N ถ้ามีไฟล์ .part อยู่)
     S -> C: 200 OK (หรือ 206)
             size, offset, checksum, whole-checksum, content-length: 8213
             <ข้อมูล 8213 ไบต์ สตรีมทีละบล็อก 256 KiB>

 8.  ไคลเอนต์: เขียนลง report.pdf.part คำนวณ hash ของแต่ละบล็อกขณะที่ข้อมูลมาถึง
               เทียบ hash ของช่วงข้อมูล   กับ  checksum        -> ต้องตรง
               เทียบ hash ของไฟล์ทั้งไฟล์ กับ  whole-checksum  -> ต้องตรง
               os.replace(report.pdf.part, report.pdf)   <- ตอนนี้เท่านั้นที่ไฟล์ปรากฏ

 9.  C -> S: QUIT * KUFT/2.0
     S -> C: 200 OK  connection: close

10.  ทั้งคู่:  TLS close_notify, TCP FIN
```

ขั้นที่ 2 และ 5 คือความปลอดภัย `content-length` ในขั้นที่ 7 คือ framing และขั้นที่ 8
คือการรับประกันความถูกต้อง — โดยลำดับตรงนั้น คือ ตรวจสอบ *ก่อน* เปลี่ยนชื่อ เป็นสิ่งที่
ทำให้มันเป็นการรับประกัน ไม่ใช่แค่การรายงานผล

## 7. ขอบเขตด้านความปลอดภัย พูดกันตรง ๆ

**อยู่ในขอบเขต และจัดการแล้ว:** การดักฟังแบบเฉย ๆ บน LAN; การดักกลางทางเชิงรุก;
การดัดแปลงเนื้อไฟล์ระหว่างทาง; การ replay การพิสูจน์ตัวตนที่ถูกดักไว้; การหลุดออก
นอก share ด้วย path traversal; การเข้าถึงโดยไม่พิสูจน์ตัวตน; การถล่มทรัพยากรด้วย
คำขอจำนวนมากหรือจำนวน connection; การแทรกเฮดเดอร์ผ่านชื่อไฟล์ที่ประดิษฐ์ขึ้น;
การโจมตีด้วยการวัดเวลาในการเปรียบเทียบ proof

**อยู่นอกขอบเขต และไม่ได้จัดการ:**

* **ไม่มีตัวตนรายบุคคล** มีรหัสเดียว ระดับความไว้วางใจเดียว ใครที่ถือรหัสก็มีสิทธิ์
  เท่ากับคนอื่นที่ถือรหัสเดียวกัน
* **`known_hosts.json` เก็บกุญแจ `K` ที่ derive แล้ว** สิทธิ์อ่านไฟล์นั้นเทียบเท่ากับ
  การถือรหัสจับคู่ของเซิร์ฟเวอร์นั้น — ระดับความไว้วางใจเดียวกับกุญแจส่วนตัวของ SSH
* **การวิเคราะห์ปริมาณทราฟฟิก** ผู้สังเกตการณ์รู้ขนาดและเวลาของทุกการโอน แม้จะไม่รู้
  ชื่อไฟล์หรือเนื้อหา
* **การเพิกถอนสิทธิ์เป็นแบบทั้งหมดหรือไม่เลย** `--new-code` เพิกถอนสิทธิ์ไคลเอนต์
  ทุกรายพร้อมกัน
* **รหัสจับคู่เป็นความลับได้เท่ากับช่องทางที่คุณใช้บอกมันเท่านั้น** อ่านจากหน้าจอ
  หรือพูดออกเสียง อย่าส่งผ่านเครือข่ายที่คุณกำลังกังวลอยู่
* **เซิร์ฟเวอร์รันในนามผู้ใช้ที่เรียกมัน ด้วยสิทธิ์ไฟล์ของผู้ใช้คนนั้น** share root
  เป็นขอบเขตเดียว — ควรรันด้วยบัญชีที่ไม่มีสิทธิ์พิเศษ

## 8. การออกแบบนี้ถูกตรวจสอบอย่างไร

`tests/test_kuft.py` — **87 การทดสอบ ผ่านทั้งหมด** (`python -m unittest discover -s tests`,
ใช้เวลา 9.5 วินาที) แบ่งเป็น 4 ชั้น:

| ชั้น | ครอบคลุม |
| --- | --- |
| **Codec โดยไม่ใช้ socket** | การ encode/decode ไป-กลับ, ช่องว่างและ Unicode ใน target, body ที่มี CRLF และ NUL, ข้อความติด ๆ กันที่ยังรักษา framing ได้, body ที่ถูกตัดขาด และการปฏิเสธ framing ทุกกรณี `400`/`405`/`505` |
| **Crypto โดยไม่ใช้ socket** | การ normalize รหัสและซ่อมอักขระที่สับสน, การขึ้นกับ salt, **การที่ proof เปลี่ยนเมื่อลายนิ้วมือเปลี่ยน**, proof ของไคลเอนต์กับเซิร์ฟเวอร์ที่ต่างกัน, ความสดใหม่ของ nonce, ความเสถียรของตัวตนข้ามการโหลด, การอ่าน-เขียน known hosts |
| **การรับ input แบบซ่อน** | prompt รับรหัสจับคู่: การ echo, backspace, ปุ่มลูกศร, Ctrl+C และ fallback เมื่อไม่มี console |
| **End-to-end บน TLS จริง** | เซิร์ฟเวอร์จริงบนพอร์ตชั่วคราว ขับด้วยไคลเอนต์จริง: การจับคู่, **รหัสผิด**, **ลายนิ้วมือเปลี่ยน**, คำขอที่ยังไม่พิสูจน์ตัวตน, การ list, การดาวน์โหลด (ข้อความ, Unicode, ไบนารี, ไฟล์ขนาดศูนย์), **การ resume**, การอัปโหลด, การปฏิเสธการทับไฟล์, **checksum ล้มเหลวโดยไม่ทิ้งร่องรอย**, mkdir/delete/move, **path traversal**, ชื่อไฟล์ที่มีช่องว่างและอักษรไทย, อัปโหลดเกินขนาด, range ที่ผิด, โหมด read-only, rate limit, ขีดจำกัดจำนวนไคลเอนต์ และ Ctrl+C ขณะว่าง |

ชุดทดสอบเขียนขึ้นให้เป็น **รูปแบบที่รันได้ของข้อกำหนด**: ทุกข้อกำหนดที่มีเลขกำกับใน
หัวข้อ conformance ของ `KUFT-2.0-spec.md` §10 มีการทดสอบที่จะล้มเหลวถ้าข้อนั้นถูก
ละเมิด ส่วน `MANUAL-TESTS.md` ครอบคลุมเนื้อหาเดียวกันด้วยการทดสอบด้วยมือ พร้อม
ค่า checksum อ้างอิง สำหรับการสาธิตบนเครื่องจริงสองเครื่อง

## 9. สิ่งที่จะปรับปรุงต่อไป

ข้อจำกัดที่ยอมรับตามจริง และสิ่งที่ต้องทำเพื่อแก้แต่ละข้อ:

1. **บัญชีผู้ใช้รายบุคคล** รหัสร่วมรหัสเดียวเป็นระดับพิธีการที่เหมาะกับเครื่องสองเครื่อง
   ของคนคนเดียว และไม่เหมาะกับห้องแล็บ การแก้ต้องมีตารางผู้ใช้ salt รายคน และการ
   ระบุตัวตนในทุกบรรทัด log
2. **การโอนแบบวนลึกทั้งไดเรกทอรี** `get -r` / `put -r` ต้องมีการแลกเปลี่ยน manifest
   หรือให้ไคลเอนต์เดินสำรวจด้วย `LIST` ตัวโปรโตคอลรองรับวิธีหลังอยู่แล้ว ขาดแค่งาน
   ฝั่งไคลเอนต์
3. **Service discovery** การต้องพิมพ์หมายเลข IP เป็นขั้นตอนที่น่ารำคาญที่สุด mDNS
   (`_kuft._tcp.local`) จะตัดขั้นตอนนั้นออกได้ — และบังเอิญว่านั่นคือจุดเดียวในโครงงานนี้
   ที่ UDP เหมาะสมอย่างแท้จริง: service discovery คือกรณี best-effort, multicast,
   ลองใหม่ที่ชั้นแอปพลิเคชัน ซึ่ง UDP ถูกสร้างมาเพื่อสิ่งนี้พอดี
4. **การบีบอัด** ทำได้ด้วยเฮดเดอร์ `content-encoding` ที่ตกลงกันตอน `HELLO` จงใจ
   ข้ามไป เพราะมันเข้ากันได้ไม่ดีกับการ resume — offset จะกลายเป็นตำแหน่งในสตรีมที่
   บีบอัดแล้ว — และได้ประโยชน์น้อยกับสื่อที่ถูกบีบอัดมาแล้ว
5. **IPv6** ตัว listener เป็น `AF_INET` อย่างเดียว การใช้ `AF_INET6` พร้อม
   `IPV6_V6ONLY=0` จะครอบคลุมทั้งสองแบบ แลกกับการต้องจัดการเรื่องเฉพาะแพลตฟอร์ม

## 10. สรุปคำตอบ

| คำถาม | คำตอบ |
| --- | --- |
| **ทำมาเพื่ออะไร** | ย้ายไฟล์โดยตรงระหว่างสองเครื่องบนเครือข่ายเดียวกัน โดยเข้ารหัสและตรวจสอบความถูกต้อง ไม่ผ่านบุคคลที่สาม ไม่ต้องมีบัญชี และไม่ต้องตั้งค่าอะไรนอกจากรหัสจับคู่หนึ่งรหัส |
| **ทำงานอย่างไร** | เซิร์ฟเวอร์แบบ multi-thread บน TLS 1.3 แชร์ไดเรกทอรีเดียวที่ถูกกักขอบเขต ไคลเอนต์จับคู่ครั้งเดียวแล้วปักหมุดใบรับรองแบบเดียวกับ SSH จากนั้นส่งคำขอผ่านโปรโตคอลเล็ก ๆ ที่มีรูปทรงแบบ HTTP ข้อมูลถูกสตรีมทีละบล็อก 256 KiB และตรวจสอบด้วย SHA-256 ก่อนที่ไฟล์จะปรากฏภายใต้ชื่อจริง |
| **ออกแบบโปรโตคอลอย่างไร** | ส่วนหัวเป็น US-ASCII ที่จบด้วยบรรทัดว่าง บวก `content-length` ที่บังคับมี — framing จึงไม่ขึ้นกับเนื้อหาของ body; target ถูก percent-encode — request line จึงมีสาม token เสมอ; เก้า method ที่แต่ละอันตรงกับปฏิบัติการบนระบบไฟล์หนึ่งอย่าง; status code ตามคลาสของ HTTP บวก `422 CHECKSUM MISMATCH`; และ proof ของการจับคู่ที่ผูกกับช่องทาง โดยใส่ลายนิ้วมือใบรับรองเข้าไปใน HMAC ซึ่งเป็นสิ่งที่ทำให้การเข้ารหัสมีความหมาย |
| **ใช้ transport service model แบบไหน และทำไม** | **TCP** — connection-oriented, เชื่อถือได้, เรียงลำดับ, ไม่ซ้ำ, เป็นสตรีมไบต์ พร้อม flow control และ congestion control ไฟล์ต้องการทุกไบต์ ครั้งเดียว ตามลำดับ ดังนั้น R1–R6 จึงตรงกับการรับประกันของ TCP พอดี การสร้างสิ่งเหล่านี้บน UDP ก็คือการเขียน TCP ใหม่ให้แย่ลง และ TLS 1.3 มีให้ใช้บน TCP ในไลบรารีมาตรฐาน ขณะที่ DTLS ไม่มี การเลือก UDP จึงเท่ากับต้องเขียนวิทยาการรหัสลับเอง หรือไม่มีการเข้ารหัสเลย ส่วนสิ่งที่ TCP ขาด — ไม่มีขอบเขตข้อความ, checksum ที่อ่อนแอและครอบคลุมแค่ทีละ hop, ไม่มีความปลอดภัย, ไม่มีสถานะ session, ไม่มีการเริ่มโอนต่อ — ถูกเติมอย่างจงใจที่ชั้นแอปพลิเคชันทุกจุด ส่วนสิ่งที่ TCP ขาดจริง ๆ อีกอย่างคือไม่รับประกันเวลาหรือ throughput ซึ่งไม่เสียหายอะไรที่นี่ เพราะในการรับส่งไฟล์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มาตรงเวลาทุกประการ |
