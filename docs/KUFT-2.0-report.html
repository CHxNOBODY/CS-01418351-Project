1. โปรแกรมนี้คืออะไร และใช้สำหรับทำอะไร

คำตอบโดยย่อ

KUFT/2.0 คือโปรแกรมรับส่งไฟล์แบบ client/server สำหรับย้ายไฟล์ โดยตรง ระหว่างคอมพิวเตอร์สองเครื่องที่อยู่บนเครือข่ายเดียวกัน โดยข้อมูลถูกเข้ารหัสตลอดเส้นทาง ทั้งสองฝั่งพิสูจน์ตัวตนซึ่งกันและกัน และไฟล์ที่รับมาถูกตรวจสอบความถูกต้องด้วย SHA-256 ก่อนถูกส่งมอบให้ผู้ใช้ ไม่ผ่านบุคคลที่สาม ไม่ต้องมีบัญชีผู้ใช้ และไม่ต้องตั้งค่าอะไรนอกจากรหัสจับคู่หนึ่งรหัส

1.1 ปัญหาที่ต้องการแก้

คอมพิวเตอร์สองเครื่องอยู่บนเครือข่ายเดียวกัน — Wi-Fi ที่บ้าน โต๊ะแล็บ หรือ hotspot จากมือถือ — เครื่องหนึ่งมีไฟล์ที่อีกเครื่องต้องการ วิธีที่คนทั่วไปใช้กันนั้น มีข้อเสียชัดเจนทุกวิธี

วิธีที่ใช้กันทั่วไปปัญหาที่แท้จริง
ส่งอีเมลหาตัวเองจำกัดขนาดไฟล์ และไฟล์ต้องผ่านเซิร์ฟเวอร์ของบุคคลที่สาม
Cloud drive / แอปแชตอัปโหลดขึ้นอินเทอร์เน็ตแล้วดาวน์โหลดกลับลงมา เพียงเพื่อย้ายไฟล์ในระยะสองเมตร ต้องมีบัญชีและต้องมีเน็ตที่ใช้งานได้
USB flash driveต้องเดินไปเสียบเอง ช้า และตัวแฟลชไดรฟ์เองก็เป็นช่องทางแพร่มัลแวร์
Windows file sharing (SMB)ใหญ่เทอะทะ ต้องตั้งค่า domain/workgroup และเป็นบริการที่ทุกคู่มือความปลอดภัยบอกให้ปิดไฟร์วอลล์กั้นไว้
ftp / python -m http.serverส่งเป็น plaintext ใครก็ตามที่อยู่บน Wi-Fi เดียวกันอ่านไฟล์ได้ และถ้าเป็น FTP ก็อ่านรหัสผ่านได้ด้วย

ทุกวิธีที่ว่ามา ไม่อ้อม ก็ไม่เข้ารหัส หรือไม่ก็ทั้งสองอย่าง KUFT จึงเกิดขึ้นเป็นคำตอบที่เล็กและตรงไปตรงมา: พิมพ์คำสั่งเดียวในแต่ละเครื่อง ไฟล์วิ่งตรงระหว่างสองเครื่องผ่านเครือข่ายภายใน

1.2 ตัวโปรแกรมประกอบด้วยอะไรบ้าง

  • โปรโตคอลชั้น Application ชื่อ KUFT/2.0 ซึ่งออกแบบขึ้นเองทั้งหมด และกำหนดเป็นเอกสารข้อกำหนดแยกต่างหาก
  • เซิร์ฟเวอร์ ที่แชร์ไดเรกทอรีเดียว และไม่ให้เข้าถึงอะไรที่อยู่เหนือขึ้นไป
  • ไคลเอนต์ ที่มี shell แบบโต้ตอบ (ls, cd, get, put, rm, mv, rn, mkdir, stat) และโหมดคำสั่งเดียวจบสำหรับเขียนสคริปต์
  • กลไกการจับคู่ (pairing) ที่ให้การพิสูจน์ตัวตนแบบสองทาง โดยไม่ต้องพึ่ง certificate authority, directory service หรือบัญชีคลาวด์ใด ๆ

การใช้งานจริงมีเพียงสองคำสั่ง:

เครื่องที่มีไฟล์      python kuft.py serve
                     → พิมพ์ที่อยู่ IP และรหัสจับคู่ออกมาบนหน้าจอ

เครื่องที่ต้องการไฟล์  python kuft.py connect 192.168.1.114
                     → พิมพ์รหัสจับคู่หนึ่งครั้ง แล้วใช้ ls / get / put ได้ทันที

1.3 เป้าหมายการออกแบบ

เรียงตามลำดับความสำคัญ เมื่อเป้าหมายขัดกัน ข้อที่อยู่บนกว่าชนะเสมอ

  1. ถูกต้อง — ไฟล์ที่ไปถึงต้องเหมือนไฟล์ต้นทางทุกไบต์ ไม่เช่นนั้นการโอนย้ายต้องล้มเหลวอย่างเห็นได้ชัด ไม่มีเส้นทางที่ข้อมูลเสียหายแบบเงียบ ๆ
  2. เป็นความลับและพิสูจน์ตัวตนได้ — ผู้โจมตีที่อยู่บน Wi-Fi เดียวกัน ต้องอ่านข้อมูลไม่ได้ และปลอมเป็นฝั่งใดฝั่งหนึ่งไม่ได้
  3. เล็กพอที่จะเข้าใจได้ทั้งหมด — รวมทั้งโครงงานไม่ถึง 4,000 บรรทัด รูปแบบข้อมูลบนสายพอดีหนึ่งหน้ากระดาษ และอ่านได้จาก packet capture โดยตรง
  4. ใช้งานได้ด้วยคำสั่งสองคำสั่ง — ถ้าต้องอ่านคู่มือก่อนใช้ ก็ถือว่าล้มเหลวตามโจทย์ที่ตั้งไว้เอง
  5. ใช้ทรัพยากรจำกัด — โอนไฟล์ 40 GB ต้องใช้หน่วยความจำเท่ากับโอนไฟล์ 4 KB

1.4 สิ่งที่จงใจไม่ทำ

  • ไม่มีบัญชีผู้ใช้รายบุคคล — มีรหัสจับคู่ร่วมรหัสเดียว ระดับความไว้วางใจเดียว เหมาะกับเครื่องสองเครื่องของคนคนเดียว ไม่เหมาะกับห้องแล็บหลายผู้ใช้
  • ไม่มี certificate authority — ใบรับรองเป็นแบบ self-signed และใช้การปักหมุด (pinning) แบบเดียวกับ SSH แทน
  • ไม่มีการโอนแบบวนลึกทั้งไดเรกทอรี — การลบและการโอนแบบวนลึก ควรเป็นลูปฝั่งไคลเอนต์ที่ผู้ใช้มองเห็นทุกขั้นตอน
  • ไม่มี service discovery — ต้องพิมพ์หมายเลข IP เอง

2. คุณลักษณะของแอปพลิเคชัน (Characteristics)

2.1 สรุปคุณลักษณะเชิงเครือข่าย

ตารางนี้คือคุณลักษณะที่กำหนดว่าโปรแกรมนี้ต้องการอะไรจากชั้น Transport ซึ่งจะถูกใช้เป็นฐานของการตัดสินใจในหัวข้อที่ 3

คุณลักษณะรายละเอียด
สถาปัตยกรรม Client/Server — ฝั่งหนึ่งรัน serve เพื่อแชร์ไดเรกทอรี อีกฝั่งรัน connect ไม่ใช่ peer-to-peer
ทิศทางข้อมูล สองทาง — ดาวน์โหลด (GET) และอัปโหลด (PUT) บน connection เดียวกัน
ลักษณะ session มีสถานะ (stateful) และอายุยาว — ทักทาย → พิสูจน์ตัวตน → ทำงานหลายคำสั่งติดกัน → ปิด
ขนาดข้อมูล ไม่จำกัดโดยธรรมชาติ — ตั้งแต่ไฟล์ศูนย์ไบต์ถึงหลายสิบกิกะไบต์ในหนึ่งข้อความ
ความทนต่อการสูญหาย ศูนย์ — ไฟล์ที่ขาดไปหนึ่งไบต์คือไฟล์เสีย ไม่ใช่ไฟล์ที่แย่ลงนิดหน่อย
ความทนต่อความหน่วง สูงมาก — ไม่ใช่งานเรียลไทม์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มาตรงเวลา
ความต้องการ throughput ยิ่งมากยิ่งดี แต่ไม่มีขั้นต่ำที่ต้องรับประกัน การโอนที่ช้ากว่ายังคงถูกต้องสมบูรณ์
ความปลอดภัย จำเป็น — ความลับ ความถูกต้อง และการพิสูจน์ตัวตนสองทาง
จำนวนผู้ใช้พร้อมกัน น้อย — ค่าเริ่มต้น 8 connection พร้อมกัน
ขอบเขตเครือข่าย LAN เดียวกันเป็นหลัก (ขยายข้ามระยะไกลได้ผ่าน VPN, port forward หรือ tunnel)

  • หนึ่ง thread ต่อหนึ่ง connection — เหมาะกับงานนี้เพราะ session มีอายุยาว มีสถานะ และถูกครอบงำด้วย blocking I/O บน socket และไฟล์ การใช้ event loop ไม่ได้ประโยชน์อะไรที่ 8 ไคลเอนต์พร้อมกัน แต่แลกมาด้วย ความซับซ้อนของโค้ดอย่างมาก

  • socket มี timeout 300 วินาที ไคลเอนต์ที่หายไปกลางคันจึงคืนช่องว่างให้ระบบ
  • accept loop ใช้การวนถามด้วย timeout 0.5 วินาที แทนการบล็อก — เป็นการแก้ปัญหาเฉพาะของ Windows ที่ไม่ขัดจังหวะ blocking socket call เมื่อกด Ctrl+C

2.4 ลักษณะของทราฟฟิกและการใช้ทรัพยากร

  • ทราฟฟิกไม่สมมาตรอย่างรุนแรง — ข้อความควบคุมมีขนาดหลักร้อยไบต์ แต่ body ของการโอนไฟล์มีขนาดหลายกิกะไบต์ การออกแบบจึงต้องแยกสองสิ่งนี้ออกจากกัน
  • สตรีมเป็นบล็อกขนาดคงที่ 256 KiB ข้อมูลไม่เคยถูกโหลดเข้าหน่วยความจำทั้งไฟล์ และค่า hash ถูกคำนวณไปพร้อมกับการสตรีม จึงไม่ต้องอ่านข้อมูลซ้ำอีกรอบเพื่อตรวจสอบ
  • หน่วยความจำคงที่ — ไฟล์ 40 GB ใช้หน่วยความจำเท่ากับไฟล์ 4 KB
  • หลายคำสั่งต่อหนึ่ง connection — TLS handshake และการจับคู่เกิดขึ้นครั้งเดียว ต้นทุนนั้นถูกกระจายไปทั่วทั้ง session

3.4 เหตุผลชี้ขาด: TLS 1.3 ทำงานบน TCP

ยังมีเหตุผลที่สองที่ปิดประเด็นนี้อย่างสิ้นเชิง และเป็นข้อที่ควรเน้น

TLS 1.3 ทำงานบน TCP และไลบรารีมาตรฐานของ Python เปิดให้ใช้ โค้ดของโครงงานนี้จึงไม่ได้เขียนวิทยาการรหัสลับเองแม้แต่บรรทัดเดียว — มันเพียง ตั้งค่า สแต็กที่ผ่านการตรวจสอบมาแล้ว

ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.minimum_version = ssl.TLSVersion.TLSv1_3      # ไม่ยอมรับอะไรที่ต่ำกว่านี้
ctx.load_cert_chain(cert_path, key_path)

ส่วนที่เทียบเท่าบน UDP คือ DTLS และโมดูล ssl ของ Python ไม่เปิดให้ใช้เลย การเลือก UDP จึงบังคับให้เกิดผลอย่างใดอย่างหนึ่ง

  1. เขียน record layer และ key exchange ขึ้นเอง ซึ่งเป็นวิธีที่แน่นอนที่สุด ในการสร้างวิทยาการรหัสลับที่พัง และเป็นความผิดพลาดที่วรรณกรรมด้านความปลอดภัย ทั้งหมดเตือนไว้ หรือ
  2. ปล่อยโปรแกรมโดยไม่มีการเข้ารหัส ซึ่งก็คือ KUFT เวอร์ชันหนึ่ง สิ่งที่เวอร์ชันนี้เกิดมาเพื่อแทนที่

ทั้งสองทางรับไม่ได้ TCP จึงไม่ใช่แค่ตัวเลือกที่ดีกว่า แต่เป็นตัวเลือกเดียวที่ทำให้โครงงานนี้มีการเข้ารหัสได้เลย

3.5 ช่องว่างใน service model ของ TCP ที่ต้องเติมเอง

TCP ไม่ได้แก้ทุกอย่างให้ Service model ของมันไม่สมบูรณ์สำหรับแอปพลิเคชันนี้ อยู่ห้าข้อ และแต่ละช่องว่างถูกเติมอย่างจงใจที่ชั้น Application

ช่องว่างทำไมจึงเป็นปัญหาสิ่งที่ KUFT เติมเข้าไป
สตรีมไบต์ไม่มีขอบเขตข้อความ send กับ recv ไม่สอดคล้องกัน หนึ่ง write อาจมาถึงเป็นสามการอ่าน หรือสาม write อาจมาถึงเป็นครั้งเดียว ฝ่ายรับจึงบอกไม่ได้ว่าข้อความจบตรงไหน Framing ที่ชัดเจน: ส่วนหัวจบด้วยบรรทัดว่าง บวก content-length ที่บังคับมี (§4.2)
TCP checksum อ่อนแอและครอบคลุมแค่ทีละ hop เป็นผลรวมแบบ one's-complement 16 บิต ออกแบบมาจับสัญญาณรบกวน คำนวณต่อ segment และถูกคำนวณใหม่โดยอุปกรณ์กลางทางทุกตัว การแก้ไขของผู้โจมตีเชิงรุกจึงผ่านฉลุย SHA-256 แบบ end-to-end ทั้งต่อช่วงข้อมูลและต่อไฟล์ทั้งไฟล์ (§4.11)
ไม่มีความลับและไม่มีการพิสูจน์ตัวตน TCP ส่ง plaintext ทั้งหมด และไม่รู้ว่าปลายทางเป็นใคร TLS 1.3 บวกกลไกจับคู่ที่ผูก proof เข้ากับใบรับรอง (§4.10)
รู้แค่ว่า "เชื่อมต่อแล้ว" ไม่รู้ว่า "พิสูจน์ตัวตนแล้ว" TCP connection ที่เปิดอยู่ไม่ได้แปลว่าคู่สนทนามีสิทธิ์ทำอะไรก็ได้ State machine ระดับแอปพลิเคชัน: ทุกคำสั่งยกเว้น HELLO และ AUTH ตอบ 401 จนกว่า proof จะผ่าน (§4.12)
connection ที่ขาดทำให้เสียการโอนทั้งครั้ง TCP กู้คืน segment ไม่ใช่ ไฟล์ ถ้า connection ตาย ดาวน์โหลด 4 GB ที่เดินมาถึง 90% ต้องเริ่มใหม่จากศูนย์ เก็บไฟล์ .part ที่ยังไม่ครบไว้ แล้วเริ่มต่อด้วยเฮดเดอร์ range (§4.11)

3.6 สิ่งที่ TCP ไม่รับประกัน แต่เราไม่ต้องการ

TCP จงใจไม่รับประกัน throughput ขั้นต่ำและไม่รับประกันขอบเขต latency สำหรับแอปพลิเคชันจำนวนมากนั่นคือข้อจำกัดที่แท้จริง แต่ที่นี่มันไม่เสียหายอะไรเลย และเหตุผลควรพูดให้ตรง

ในการรับส่งไฟล์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มาตรงเวลาทุกประการ

ไม่มีอะไรถูกนำไปใช้จนกว่าไฟล์ทั้งไฟล์จะมาถึงและ hash ผ่าน การโอนที่หยุดชะงัก ไปสองวินาทีแล้วไปต่อ ให้ผลลัพธ์เหมือนกันทุกไบต์ ดังนั้นการที่ TCP ยอมแลก latency เพื่อความน่าเชื่อถือ — รอ retransmission หรือลด congestion window ลงครึ่งหนึ่ง — เป็นการแลกที่โครงงานนี้ ยินดีเสมอ

4. การออกแบบ Application-Layer Protocol

หัวข้อนี้คือข้อกำหนดของโปรโตคอล KUFT/2.0 อย่างละเอียด ครอบคลุมรูปแบบข้อความ ชุดคำสั่ง เฮดเดอร์ รหัสสถานะ และ request/response messages ทุกคู่ ที่ใช้สื่อสารระหว่าง Client และ Server

4.1 ข้อจำกัดที่การออกแบบต้องทำให้ได้

  1. Framing ต้องไม่ขึ้นกับเนื้อหาของ body — ไฟล์ไบนารีมีทุกไบต์ที่เป็นไปได้ รวมทั้ง CRLF และ NUL การแบ่งข้อความต้องไม่ถูกรบกวนจากเนื้อหาไฟล์
  2. ต้องสตรีมได้ — ห้ามโหลดไฟล์ทั้งไฟล์เข้าหน่วยความจำ
  3. ต้องรองรับชื่อไฟล์ทุกแบบ — เว้นวรรค วงเล็บ อักษรไทย อีโมจิ
  4. ต้องอ่านได้จาก packet capture — เพื่อให้ดีบักและตรวจสอบได้
  5. ต้องกันการใช้หน่วยความจำไม่จำกัด — คู่สนทนาที่ไม่หวังดีต้องทำให้ เซิร์ฟเวอร์จองหน่วยความจำไม่จำกัดไม่ได้

4.2 รูปแบบข้อความ

ข้อความของ KUFT คือ ส่วนหัวที่เป็นข้อความ บรรทัดว่างหนึ่งบรรทัด แล้วตามด้วย body ไบนารีที่นับจำนวนไว้แล้ว

message   = head CRLF [ body ]
head      = start-line CRLF *( header CRLF )
header    = field-name ":" OWS field-value
  • start-line เป็น US-ASCII
  • ชื่อเฮดเดอร์ไม่สนใจตัวพิมพ์เล็กใหญ่ และถูกแปลงเป็นตัวพิมพ์เล็กเมื่อรับ
  • ค่าเฮดเดอร์เป็น UTF-8 และต้องไม่มี CR หรือ LF ตัว encoder จะปฏิเสธที่จะเข้ารหัสค่าที่มีอักขระเหล่านี้ ซึ่งเป็นสิ่งที่ปิดช่องโหว่ header injection
  • ส่วนหัวจบที่บรรทัดว่างแรก
  • มี body ก็ต่อเมื่อ มีเฮดเดอร์ content-length ที่ไม่เป็นศูนย์ body มีขนาดเท่านั้นพอดี และไม่ถูกตีความใด ๆ จึงมี CRLF, NUL หรือไบต์อะไรก็ได้โดยไม่ต้อง escape
ทำไมจึงเลือกรูปทรงแบบ HTTP

นี่คือรูปแบบของ HTTP และการหยิบยืมนี้เป็นความตั้งใจ: มันคือ framing ชั้นแอปพลิเคชันที่ประสบความสำเร็จที่สุดเท่าที่เคยมีการใช้งานมา อ่านออกได้ทันที และคุณสมบัติของมันเป็นที่เข้าใจกันดี สิ่งที่ ไม่ได้ หยิบยืมมา คือความซับซ้อนที่ HTTP สะสมมา — ไม่มี chunked encoding, ไม่มี content negotiation, ไม่มี cookie, ไม่มี caching

ทางเลือกที่พิจารณาแล้วไม่เลือก: binary TLV กะทัดรัดดี แต่มองไม่เห็นใน packet capture และไบต์ที่ประหยัดได้ไม่มีความหมายเลยเมื่อเทียบกับ body ขนาดหลายกิกะไบต์ · JSON บรรทุกข้อมูลไบนารีดิบไม่ได้ถ้าไม่ base64 ซึ่งเพิ่มขนาด 33% ในทุก ๆ ไฟล์

4.3 Request line และ Status line

Request line

request-line = method SP target SP "KUFT/2.0"

target ถูก percent-encode: ทุกอ็อกเท็ตที่อยู่นอก A-Z a-z 0-9 / * - . _ ~ ถูกเขียนเป็น %XX บนการเข้ารหัส UTF-8 ของมัน สิ่งนี้รับประกันว่า request line มี สาม token คั่นด้วยช่องว่างเสมอ ไม่ว่าไฟล์จะชื่ออะไร และทำให้ชื่อ Unicode ทุกแบบโอนได้ครบถ้วน

GET /Quarterly%20Report%20(final).pdf KUFT/2.0
PUT /%E0%B8%A3%E0%B8%B2%E0%B8%A2%E0%B8%87%E0%B8%B2%E0%B8%99.txt KUFT/2.0

Status line

status-line = "KUFT/2.0" SP status-code SP reason-phrase

4.4 การตัดสินใจสี่ข้อเรื่อง framing

การตัดสินใจผลที่ตามมา
1. ส่วนหัวเป็น ASCII และจบที่บรรทัดว่างแรก Parser ไม่เคยตรวจสอบ body เลย ไฟล์จึงมี CRLF, NUL หรืออะไรก็ได้ โดยไม่ต้อง escape และไม่มีต้นทุน ถ้าใช้ end marker แทน จะต้องสแกนหา marker ใน body ซึ่งแปลว่าต้อง escape marker ภายใน body ซึ่งแปลว่า framing ขึ้นกับเนื้อหา นั่นคือกฎที่ยืนยันว่าจะไม่ยอมละเมิด
2. content-length บังคับมีเสมอเมื่อมี body ฝ่ายรับรู้แน่นอนว่าต้องอ่านกี่ไบต์ และไม่ต้องเดาว่าข้อความจบตรงไหน ทำให้ส่งข้อความติด ๆ กันบน connection เดียวได้อย่างปลอดภัย และเป็นสิ่งที่ทำให้ สตรีมได้ — อ่านตามจำนวนที่รู้แล้ว ทีละบล็อก 256 KiB ตรงเข้าไฟล์ปลายทาง คำนวณ hash ไปด้วยระหว่างทาง ไฟล์ 40 GB ใช้หน่วยความจำเท่ากับไฟล์ 4 KB
3. Target ถูก percent-encode รับประกันว่า request line มีสาม token เสมอ ถ้าไม่มีมัน GET Quarterly Report final.pdf KUFT/2.0 จะถูกแยกเป็นห้า token และ parse ไม่ผ่าน — ซึ่งเป็นจุดที่เวอร์ชันหนึ่งพังจริง ๆ
4. ทุกความยาวที่คู่สนทนามีอิทธิพลต่อได้ มีเพดานตายตัว คู่สนทนาที่ส่งบรรทัดเฮดเดอร์โดยไม่มีตัวจบบรรทัด จะทำให้เซิร์ฟเวอร์ จองหน่วยความจำไม่จำกัดไม่ได้ (ดู §4.5)
กฎเล็ก ๆ ที่ปิดช่องโหว่จริง

ตัว encoder ปฏิเสธที่จะส่งค่าเฮดเดอร์ที่มี CR หรือ LF ถ้าไม่มีข้อนี้ ชื่อไฟล์ที่มีตัวขึ้นบรรทัดใหม่อยู่ข้างในสามารถแทรกเฮดเดอร์ปลอม หรือแทรกแม้กระทั่ง status line ปลอม เข้าไปในคำตอบได้ การปฏิเสธตั้งแต่ตอน encode หมายความว่าไม่มีผู้เรียกใช้รายไหนเปิดช่องโหว่นี้ได้เลย

4.8 รหัสสถานะ (Status codes)

ใช้รหัสสามหลักตามคลาสของ HTTP เพื่อให้ คลาส มีความหมาย แม้ผู้รับจะไม่รู้จักรหัสเฉพาะตัวนั้น — 2xx สำเร็จ, 4xx เป็นความผิดของไคลเอนต์, 5xx เป็นความผิดของเซิร์ฟเวอร์

Success

รหัสวลีเมื่อไร
200OKคำขอสำเร็จ; PUT ทับไฟล์ที่มีอยู่แล้ว
201CREATEDPUT หรือ MKDIR สร้างของใหม่
204NO CONTENTDELETE สำเร็จ
206PARTIAL CONTENTGET ที่มี range; body เป็นส่วนท้ายของไฟล์

Client errors

รหัสวลีเมื่อไร
400BAD REQUESTFraming ที่ parse ไม่ได้ — ปิด connection หลังจากนั้น
401UNAUTHORIZEDยังไม่พิสูจน์ตัวตน หรือ proof ตรวจไม่ผ่าน
403FORBIDDENpath หลุดออกนอกไดเรกทอรีที่แชร์, เซิร์ฟเวอร์เป็น read-only, หรือเป้าหมายคือรากที่แชร์
404NOT FOUNDไม่มีไฟล์หรือไดเรกทอรีนั้น
405METHOD NOT ALLOWEDคำสั่งที่ไม่รู้จัก
409CONFLICTเป้าหมายมีอยู่แล้วและไม่ได้ขอทับ; หรือไดเรกทอรีไม่ว่าง

Server errors

รหัสวลีเมื่อไร
500INTERNAL ERRORความล้มเหลวที่ไม่คาดคิดขณะจัดการคำขอที่ถูกต้อง

ความหมายคือ คำขอถูกต้องตามรูปแบบ และข้อมูลมาถึงครบตามที่ชั้น transport รับรู้ แต่ payload ไม่ตรงกับ checksum ที่ผู้ส่งประกาศไว้ ไม่มีรหัส HTTP ใดหมายความแบบนั้น และนี่คือความล้มเหลวที่สำคัญที่สุดที่โปรโตคอลนี้ต้องรายงานได้ เพราะมันคือจุดที่ ความถูกต้องแบบ end-to-end (R8) ถูกบังคับใช้จริง

4.10 กลไกจับคู่ (Pairing exchange)

นี่คือส่วนที่ทำให้การเข้ารหัสมีความหมาย จึงกำหนดไว้อย่างแม่นยำ

ปัญหา

TLS ให้ช่องทางที่เป็นความลับ — แต่ใบรับรองของเซิร์ฟเวอร์เป็นแบบ self-signed บนเครือข่ายที่มีแค่แล็ปท็อปสองเครื่อง ไม่มี certificate authority ให้อ้างอิง ใบรับรองเพียงลำพังจึงไม่พิสูจน์อะไรเลย ผู้โจมตีสร้างขึ้นเองได้ง่ายพอ ๆ กับเรา และการเข้ารหัสไปหาคู่สนทนา ที่ไม่รู้ว่าเป็นใคร แทบไม่มีค่า — มันป้องกันคนที่นั่งฟังเฉย ๆ ได้ แต่ไม่ป้องกันคนที่แทรกอยู่ตรงกลางเลย

แนวคิดหลัก

ผูก proof ของการพิสูจน์ตัวตนเข้ากับใบรับรองที่ถูกนำเสนอจริง

4.10.1 ค่าที่เกี่ยวข้อง

สัญลักษณ์นิยาม
codeอักขระ 12 ตัวจาก RFC 4648 base32 — 60 บิต ไม่สนใจตัวพิมพ์ ละเว้นขีด และอ่าน 0 1 8 9 เป็น O I B G (ชุดอักขระจึงไม่มีเลขที่สับสนกับตัวอักษรเวลาอ่านออกเสียง)
salt16 อ็อกเท็ตสุ่ม สร้างครั้งเดียวต่อเซิร์ฟเวอร์และเก็บไว้

4.10.4 การโจมตีแบบดักกลางทางล้มเหลวอย่างไร

สมมติผู้โจมตีแทรกอยู่ตรงกลาง ปิด TLS ทั้งสองด้านด้วยใบรับรองของตัวเอง ซึ่งมีลายนิ้วมือ FP'

  1. ไคลเอนต์คำนวณ proof บน FP' เพราะนั่นคือใบรับรองที่มันถูกนำเสนอ
  2. ผู้โจมตีส่ง proof นั้นต่อไปยังเซิร์ฟเวอร์จริง — มันคำนวณใหม่ไม่ได้ เพราะการคำนวณใหม่ต้องใช้ K
  3. เซิร์ฟเวอร์ตรวจ proof เทียบกับ FP ซึ่งเป็นลายนิ้วมือของตัวเอง
  4. FP ≠ FP' MAC จึงไม่ตรงกัน และเซิร์ฟเวอร์ตอบ 401

ผู้โจมตีซ่อมสถานการณ์นี้ไม่ได้ถ้าไม่มี K และหา K ไม่ได้ ถ้าไม่มีรหัส — และรหัสนั้นไม่เคยวิ่งผ่านเครือข่ายในรูปแบบใดเลย ไม่ได้เข้ารหัสส่ง ไม่ได้ hash ส่ง ไม่ได้ส่งเลย ผู้ใช้อ่านมันจากหน้าจอ proof ที่ถูกดักได้จึงให้เพียงการโจมตีแบบ offline ต่อ 60 บิต ที่มี PBKDF2 200,000 รอบขวางอยู่

4.10.6 การปักหมุด (Pinning)

เมื่อการแลกเปลี่ยนสำเร็จครั้งแรก ไคลเอนต์เก็บ FP และ K ไว้คู่กับ host:port ใน ~/.kuft/known_hosts.json การเชื่อมต่อครั้งต่อ ๆ ไปจึงข้ามการใส่รหัสไปเลยและใช้ K เดิม

ถ้า FP ที่เก็บไว้ไม่ตรงกับที่ถูกนำเสนอ ไคลเอนต์ ยกเลิกการเชื่อมต่อทันที ไม่มี prompt ให้กดยืนยัน

นั่นเป็นการตัดสินใจออกแบบโดยเจตนา ไม่ใช่การลืมใส่ ลายนิ้วมือที่เปลี่ยนหมายถึง อย่างใดอย่างหนึ่ง: เซิร์ฟเวอร์ถูกสร้างใหม่ หรือคุณกำลังถูกดักอยู่ — และกล่องข้อความให้กดยืนยัน คือวิธีที่คนกดผ่านกรณีหลังพอดี การกู้คืนจึงต้องใช้คำสั่งแยกต่างหากอย่างตั้งใจ คือ kuft.py forget <host> ซึ่งบังคับให้ผู้ใช้ต้องหยุดแล้วคิด

4.11 ความหมายของการโอนย้าย

4.11.1 ดาวน์โหลด

GET ตอบกลับด้วย size, checksum (ของช่วงข้อมูลที่ส่ง), whole-checksum (ของไฟล์ทั้งไฟล์) และ body

  1. ไคลเอนต์เขียนข้อมูลลงไฟล์ <ชื่อ>.part และคำนวณ hash ไปพร้อมกับการเขียน จึงไม่ต้องอ่านซ้ำ
  2. เทียบกับ checksum ของช่วงข้อมูล
  3. เมื่อสำเร็จ hash ไฟล์ที่ประกอบเสร็จแล้วเทียบกับ whole-checksum
  4. ทั้งสองต้องผ่าน จึงจะเปลี่ยนชื่อ .part เป็นชื่อจริง
  5. ถ้าล้มเหลว ไฟล์ .part จะยังอยู่ — ซึ่งเป็นสิ่งที่ทำให้ ครั้งถัดไปทำต่อได้ด้วย range แทนที่จะเริ่มใหม่

4.11.2 อัปโหลด — เป็นแบบ atomic

  1. เซิร์ฟเวอร์เขียน body ลงไฟล์ชั่วคราว ในไดเรกทอรีปลายทาง
  2. คำนวณ hash และเทียบกับ checksum ที่ไคลเอนต์ประกาศไว้
  3. จึงค่อย os.replace() เข้าตำแหน่งจริง

เพราะไฟล์ชั่วคราวอยู่ไดเรกทอรีเดียวกับปลายทาง การเปลี่ยนชื่อจึงอยู่ในระบบไฟล์ เดียวกันและเป็น atomic และการเปลี่ยนชื่อเกิดหลัง checksum ตรงเท่านั้น ดังนั้น การอัปโหลดที่ขาดตอนหรือถูกดัดแปลง ไม่มีทางทับไฟล์ดี ๆ ได้เลย ไฟล์เวอร์ชันเดิมรอดโดยไม่ถูกแตะต้อง

หากมีเฮดเดอร์ range: N เซิร์ฟเวอร์จะต่อท้ายจากตำแหน่ง N โดยมีเงื่อนไขว่าขนาดไฟล์ปัจจุบันต้องเท่ากับ N พอดี มิฉะนั้นตอบ 416

4.13 การกักขอบเขต (Jail)

ทุก target ถูก resolve เทียบกับรากที่แชร์ แล้วจึงตรวจว่าเป็นรากนั้นเอง หรือเป็นลูกหลานของมัน การ resolve จะยุบ .. และ ตาม symlink ก่อนการตรวจ ดังนั้น symlink ที่ชี้ออกนอกไดเรกทอรีที่แชร์ จึงถูกปฏิเสธเช่นเดียวกับ ../ ที่เขียนตรง ๆ

ความล้มเหลวตอบเป็น 403 เสมอ ไม่ใช่ 404 และคำตอบไม่เปิดเผยว่า path ข้างนอกนั้นมีอยู่จริงหรือไม่

5. สรุปคำตอบ

คำถามคำตอบ
เป็นโปรแกรมอะไร ใช้ทำอะไร โปรแกรมรับส่งไฟล์แบบ client/server ที่ย้ายไฟล์โดยตรงระหว่างสองเครื่อง บนเครือข่ายเดียวกัน โดยเข้ารหัสและตรวจสอบความถูกต้อง ไม่ผ่านบุคคลที่สาม ไม่ต้องมีบัญชี และไม่ต้องตั้งค่าอะไรนอกจากรหัสจับคู่หนึ่งรหัส
มีคุณลักษณะอย่างไร Client/server, session แบบมีสถานะและอายุยาว, ข้อมูลสองทาง, ขนาดไฟล์ไม่จำกัด, ทนต่อการสูญหายเป็นศูนย์ แต่ ทนต่อความหน่วงได้สูงมาก, ต้องการความปลอดภัยเต็มรูปแบบ, ผู้ใช้พร้อมกันน้อย (8 ราย), หนึ่ง thread ต่อหนึ่ง connection และใช้หน่วยความจำคงที่ด้วยการสตรีมทีละ 256 KiB
ใช้ service model ใด เพราะอะไร TCP — connection-oriented, เชื่อถือได้, เรียงลำดับ, ไม่ซ้ำ, เป็นสตรีมไบต์ พร้อม flow control และ congestion control ความต้องการ R1–R6 ตรงกับการรับประกันของ TCP พอดี การสร้างสิ่งเหล่านี้บน UDP ก็คือการเขียน TCP ใหม่ให้แย่ลง และเหตุผลชี้ขาดคือ TLS 1.3 มีให้ใช้บน TCP ในไลบรารีมาตรฐาน ขณะที่ DTLS ไม่มี การเลือก UDP จึงเท่ากับต้องเขียนวิทยาการรหัสลับเอง หรือไม่มีการเข้ารหัสเลย ส่วนสิ่งที่ TCP ขาดถูกเติมที่ชั้นแอปพลิเคชันทุกจุด และสิ่งเดียวที่มันขาดจริง ๆ คือการไม่รับประกันเรื่องเวลา ซึ่งไม่เสียหายอะไรเลย เพราะในการรับส่งไฟล์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มาตรงเวลาทุกประการ
ออกแบบโปรโตคอลอย่างไร ส่วนหัวเป็น US-ASCII ที่จบด้วยบรรทัดว่าง บวก content-length ที่บังคับมี — framing จึงไม่ขึ้นกับเนื้อหาของ body; target ถูก percent-encode — request line จึงมีสาม token เสมอ; เก้าคำสั่งที่แต่ละอันตรงกับปฏิบัติการบน ระบบไฟล์หนึ่งอย่าง; รหัสสถานะตามคลาสของ HTTP บวก 422 CHECKSUM MISMATCH; และ proof ของการจับคู่ที่ผูกกับช่องทาง โดยใส่ลายนิ้วมือใบรับรองเข้าไปใน HMAC ซึ่งเป็นสิ่งที่ทำให้การเข้ารหัสมีความหมาย
