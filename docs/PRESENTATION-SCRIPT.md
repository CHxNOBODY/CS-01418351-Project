## วิธีใช้สคริปต์นี้

* ข้อความใน **ย่อหน้าปกติ** คือสิ่งที่พูด เขียนแบบภาษาพูด ไม่ใช่ภาษาเขียน —
  ให้พูดออกมา อย่าอ่านตามตัวอักษร
* `[แสดง: ...]` คือสิ่งที่ต้องขึ้นจอหรือเปลี่ยนสไลด์
* `[พิมพ์: ...]` คือคำสั่งที่พิมพ์สดหน้าเวที
* **ข้อความตัวหนา** คือประโยคที่ควรเน้น พูดช้าลงตรงนั้น
* เวลาที่กำกับไว้เป็นเวลาต่อหัวข้อ ถ้าเกินเวลา ให้ตัด §5 และ §7 ก่อน ส่วน §3 และ §4
  ห้ามตัด เพราะเป็นเนื้อหาที่ถูกให้คะแนน
* ท้ายไฟล์มี **ฉบับย่อ 5 นาที** ไว้ใช้เมื่อเวลาไม่พอ และมีหัวข้อ **เตรียมตอบคำถาม**
  ที่ควรอ่านก่อนขึ้นเวทีเสมอ แม้จะไม่ได้ใช้ก็ตาม
* **คำลงท้าย:** สคริปต์นี้เขียนไว้เป็น "ครับ/ค่ะ" ให้เลือกใช้ตามผู้พูด

### ก่อนเริ่ม — เช็กลิสต์การเตรียมตัว

1. เครื่องสองเครื่องบนเครือข่ายเดียวกัน (ใช้ hotspot จากมือถือน่าเชื่อถือที่สุด —
   Wi-Fi ของมหาวิทยาลัยและที่สาธารณะหลายแห่งกันไม่ให้ไคลเอนต์คุยกันเอง ซึ่งจะทำให้
   สาธิตไม่ได้เลย)
2. ทั้งสองเครื่อง: `python kuft.py doctor` → ต้องเขียวหมด
3. ทั้งสองเครื่อง: `python make_testdata.py` → สร้างโฟลเดอร์ `share/` และ `outbox/`
4. ลบ `~/.kuft/known_hosts.json` บนเครื่องไคลเอนต์ เพื่อให้การสาธิตแสดง
   **การจับคู่ครั้งแรก** ไม่ใช่การเชื่อมต่อเงียบ ๆ (หรือใช้ `python kuft.py forget <host>`
   เพื่อลบเฉพาะเซิร์ฟเวอร์เครื่องนั้น)
5. เปิดเทอร์มินัลสองหน้าต่างให้เห็นพร้อมกัน — เซิร์ฟเวอร์ซ้าย ไคลเอนต์ขวา การสาธิต
   ทั้งหมดคือบทสนทนาระหว่างสองฝั่ง ผู้ฟังต้องเห็นทั้งคู่
6. ขยายขนาดตัวอักษร คนหลังห้องต้องอ่านลายนิ้วมือใบรับรองออก

## §3 — ชั้น Transport: ใช้ service model แบบไหน และทำไม (3 นาทีครึ่ง)

`[แสดง: ตารางเปรียบเทียบ service model ของ TCP กับ UDP จาก DESIGN.md §3.2]`

นี่คือการตัดสินใจหลักด้านเครือข่าย จึงอยากให้เหตุผลอย่างเป็นระบบ ไม่ใช่แค่ประกาศ
คำตอบออกมาเฉย ๆ

### เริ่มจากความต้องการ ไม่ใช่จากชื่อโปรโตคอล

ก่อนจะเลือก transport ผม/ดิฉันเขียนออกมาก่อนว่าแอปพลิเคชันนี้ต้องการอะไรจริง ๆ
ในรูปของ **คุณสมบัติ**

**ทุกไบต์ต้องไปถึง** — ไฟล์ที่ขาดไปหนึ่งไบต์ไม่ใช่ไฟล์ที่แย่ลงนิดหน่อย มันคือไฟล์เสีย
**ต้องเรียงลำดับ** — ไบต์ที่ห้าล้านหนึ่งต้องถูกเขียนหลังไบต์ที่ห้าล้าน **ต้องไม่ซ้ำ** —
บล็อกที่ถูกเขียนสองครั้งจะเลื่อนทุกอย่างหลังจากนั้นทั้งหมด **ต้องมี flow control** —
เครื่องที่อ่านจาก SSD ผลิตข้อมูลได้เร็วกว่าที่แล็ปท็อปซึ่งเขียนลงดิสก์ช้า ๆ จะรับไหว
ต้องมีอะไรสักอย่างคอยดันกลับ **ต้องมี congestion control** — เพราะการอัดข้อมูลเต็ม
ลิงก์ที่ใช้ร่วมกันโดยไม่ยอมถอยเป็นการเอาเปรียบคนอื่น และในระดับใหญ่ทำให้เกิด
congestion collapse และสุดท้าย **ต้องมีความหมายของ connection** เพราะ session ของ
เรามีสถานะ: ทักทายแล้ว พิสูจน์ตัวตนแล้ว พร้อมทำงาน

หกความต้องการ ทีนี้ดูว่า TCP ให้อะไรบ้าง

`[แสดง: ตารางจับคู่ความต้องการกับกลไก จาก DESIGN.md §3.3]`

ทุกข้อล้วนเป็นการรับประกันของ TCP ไม่สูญหาย — retransmission เรียงลำดับ —
sequence number ไม่ซ้ำ — sequence number อีกเช่นกัน flow control — receive window
congestion control — AIMD และ slow start ความหมายของ connection — three-way
handshake

ดังนั้นผม/ดิฉันจึงใช้ **TCP**: `AF_INET`, `SOCK_STREAM` พอร์ตเริ่มต้น 5150

### เหตุผลที่ไม่เลือก UDP สรุปได้ในประโยคเดียว

ดูคอลัมน์ขวามือของตารางนั้น — สิ่งที่ UDP จะทำให้ต้องเสีย sequence number
acknowledgement retransmission timer การประมาณ RTT reorder buffer การตรวจจับ
ข้อมูลซ้ำ windowing congestion window และนโยบายถอย

**รายการนั้นก็คือ TCP** การทำตามความต้องการเหล่านี้บน UDP คือการเขียน TCP ขึ้นมา
ใหม่ — และจะเป็นเวอร์ชันที่นักศึกษาคนเดียวเขียนในหนึ่งเทอม ไม่เคยผ่านการตรวจสอบ
และรันบนเครือข่ายเดียวเท่านั้น ส่วน TCP ของจริงถูกโจมตีและตรวจสอบมาตั้งแต่ปี 1981
และอยู่ใน kernel ซึ่งมองเห็น socket buffer และ timer ได้จริง ๆ

### เหตุผลชี้ขาดคือ TLS

แต่ยังมีเหตุผลที่สองที่ปิดประเด็นนี้อย่างสิ้นเชิง และนี่คือข้อที่อยากเน้น

**TLS 1.3 ทำงานบน TCP** และไลบรารีมาตรฐานของ Python เปิดให้ใช้ โค้ดของผม/ดิฉัน
ไม่ได้เขียนวิทยาการรหัสลับเองเลยแม้แต่บรรทัดเดียว — มันแค่ *ตั้งค่า* สแต็กที่ผ่านการ
ตรวจสอบมาแล้ว สามบรรทัด: สร้าง context, ตั้ง minimum version เป็น TLS 1.3, โหลด
ใบรับรอง

**ส่วนที่เทียบเท่าบน UDP คือ DTLS และโมดูล `ssl` ของ Python ไม่เปิดให้ใช้เลย**

การเลือก UDP จึงบังคับให้เกิดผลอย่างใดอย่างหนึ่ง หนึ่ง — เขียน record layer และ
key exchange ขึ้นเอง ซึ่งเป็นวิธีที่แน่นอนที่สุดในการสร้างวิทยาการรหัสลับที่พัง และ
เป็นความผิดพลาดที่วรรณกรรมด้านความปลอดภัยทั้งหมดเตือนไว้ หรือสอง — ปล่อย
โปรแกรมโดยไม่มีการเข้ารหัส ซึ่งก็คือ KUFT เวอร์ชันหนึ่ง สิ่งที่เวอร์ชันนี้เกิดมาเพื่อ
แทนที่

ทั้งสองทางรับไม่ได้ TCP จึงไม่ใช่แค่ตัวเลือกที่ดีกว่า แต่ **เป็นตัวเลือกเดียวที่ทำให้
โครงงานนี้มีการเข้ารหัสได้เลย**

### สิ่งที่ TCP *ไม่ได้* ให้ — และนี่คือครึ่งที่น่าสนใจ

`[แสดง: ตาราง "ช่องว่างใน service model ของ TCP" จาก DESIGN.md §3.5]`

ผม/ดิฉันไม่อยากให้เข้าใจว่า TCP แก้ทุกอย่างให้แล้ว Service model ของมันไม่สมบูรณ์
สำหรับแอปพลิเคชันนี้จริง ๆ อยู่ห้าข้อ และแต่ละช่องว่างถูกเติมอย่างจงใจที่ชั้น
Application

**หนึ่ง สตรีมไบต์ไม่มีขอบเขตข้อความ** `send` กับ `recv` ไม่สอดคล้องกัน หนึ่ง write
อาจมาถึงเป็นสามการอ่าน หรือสาม write อาจมาถึงเป็นครั้งเดียว ฝ่ายรับจึงบอกไม่ได้ว่า
ข้อความจบตรงไหน นั่นคือเหตุผลที่ต้องมี framing ที่ชัดเจน ซึ่งจะพูดในหัวข้อที่สี่

**สอง TCP checksum อ่อนแอและครอบคลุมแค่ทีละ hop** มันคือผลรวมแบบ
one's-complement 16 บิต ออกแบบมาจับสัญญาณรบกวน คำนวณต่อ segment และ
**ถูกคำนวณใหม่โดยอุปกรณ์กลางทางทุกตัว** การแก้ไขของผู้โจมตีเชิงรุกจึงผ่านฉลุย
แถมมันไม่บอกอะไรเลยเกี่ยวกับสิ่งที่ดิสก์ของผม/ดิฉันเขียนลงไปจริง ๆ ผม/ดิฉันจึงทำ
SHA-256 แบบ end-to-end นี่คือการใช้ end-to-end argument ตามตัวอักษร:
**การตรวจสอบเดียวที่มีความหมาย คือการตรวจสอบที่ปลายทางทั้งสอง**

**สาม TCP ไม่มีความลับและไม่มีการพิสูจน์ตัวตนคู่สนทนา** จึงต้องมี TLS บวกกับกลไก
จับคู่ในหัวข้อที่สี่

**สี่ TCP รู้แค่ว่า "เชื่อมต่อแล้ว" แต่ไม่รู้ว่า "พิสูจน์ตัวตนแล้ว"** จึงต้องมี state machine
ระดับแอปพลิเคชัน: ทุกคำสั่งยกเว้น `HELLO` และ `AUTH` ตอบ `401` จนกว่า proof จะผ่าน

**ห้า connection ที่ขาดทำให้เสียการโอนทั้งครั้ง** TCP กู้คืน *segment* ไม่ใช่ *ไฟล์* —
ถ้า connection ตาย ดาวน์โหลดสี่กิกะไบต์ที่เดินมาถึงเก้าสิบเปอร์เซ็นต์ต้องเริ่มใหม่จาก
ศูนย์ ผม/ดิฉันจึงเก็บไฟล์ที่ยังไม่ครบไว้ แล้วเริ่มต่อจากตำแหน่งเดิม

### และสิ่งที่ TCP ไม่ให้ แต่เราไม่ต้องการ

TCP จงใจ **ไม่รับประกัน throughput ขั้นต่ำและไม่รับประกันขอบเขต latency** สำหรับ
แอปพลิเคชันจำนวนมากนั่นคือข้อจำกัดที่แท้จริง แต่ที่นี่มันไม่เสียหายอะไรเลย และเหตุผล
ควรพูดให้ตรง:

**ในการรับส่งไฟล์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มาตรงเวลาทุกประการ**

ไม่มีอะไรถูกนำไปใช้จนกว่าไฟล์ทั้งไฟล์จะมาถึงและ hash ผ่าน การโอนที่หยุดชะงักไป
สองวินาทีแล้วไปต่อ ให้ผลลัพธ์เหมือนกันทุกไบต์ ดังนั้นการที่ TCP ยอมแลก latency
เพื่อความน่าเชื่อถือ — รอ retransmission หรือลด congestion window ลงครึ่งหนึ่ง —
เป็นการแลกที่ผม/ดิฉัน *ยินดีเสมอ*

และนั่นก็เป็นจุดที่บอกด้วยว่าเมื่อไรควรเลือก UDP แทน: **เมื่อ datagram ที่มาช้าถือว่า
ไร้ค่า ไม่ใช่แค่ล่าช้า** เสียงสด — แพ็กเก็ตที่มาช้าสี่ร้อยมิลลิวินาทีไม่เหลือช่วงเวลาให้เล่น
แล้ว การกลบช่องว่างดีกว่าการรอ สถานะเกม — ข้อมูลอัปเดตชิ้นถัดไปแทนที่ชิ้นก่อนหน้า
การส่งสถานะเก่าซ้ำมีแต่โทษ DNS — การทำ handshake แพงกว่าตัวคำถามเสียอีก
multicast — TCP ทำไม่ได้เลย

ไม่มีข้อไหนตรงกับการย้ายไฟล์

## §4 — ออกแบบโปรโตคอลอย่างไร (4 นาที)

`[แสดง: บล็อกรูปแบบข้อความจาก DESIGN.md §4.2]`

### รูปแบบ

ข้อความของ KUFT คือ **ส่วนหัวที่เป็นข้อความ บรรทัดว่างหนึ่งบรรทัด แล้วตามด้วย
body ไบนารีที่นับจำนวนไว้แล้ว**

```
GET /report.pdf KUFT/2.0
range: 0
                                  <- บรรทัดว่างปิดส่วนหัว

KUFT/2.0 200 OK
content-length: 8213
checksum: sha256=1f3a...
whole-checksum: sha256=1f3a...
detail: sending report.pdf

<ข้อมูล 8213 ไบต์พอดี ไม่ถูกตีความใด ๆ>
```

นั่นคือรูปแบบของ HTTP และการหยิบยืมนี้เป็นความตั้งใจ: มันคือ framing ชั้น
แอปพลิเคชันที่ประสบความสำเร็จที่สุดเท่าที่เคยมีการใช้งานมา ทุกคนในห้องนี้อ่านออกอยู่
แล้ว และคุณสมบัติของมันเป็นที่เข้าใจกันดี สิ่งที่ **ไม่ได้** หยิบยืมมาคือความซับซ้อนที่
HTTP สะสมมา — ไม่มี chunked encoding ไม่มี content negotiation ไม่มี cookie ไม่มี
caching

ผม/ดิฉันพิจารณา binary TLV ด้วย — กะทัดรัดดี แต่มองไม่เห็นใน packet capture และ
ไบต์ที่มันประหยัดได้ไม่มีความหมายเลยเมื่อเทียบกับ body ขนาดหลายกิกะไบต์ และ
พิจารณา JSON — ซึ่งบรรทุกข้อมูลไบนารีดิบไม่ได้ถ้าไม่ base64 ซึ่งเพิ่มขนาดสามสิบสาม
เปอร์เซ็นต์ในทุก ๆ ไฟล์

### สี่การตัดสินใจที่ทำให้ framing ทำงานได้

**หนึ่ง: ส่วนหัวเป็น ASCII และจบที่บรรทัดว่างแรก** ผลที่ตามมาคือ parser
**ไม่เคยตรวจสอบ body เลย** — ไฟล์จึงมี CRLF, NUL หรืออะไรก็ได้ โดยไม่ต้อง escape
และไม่มีต้นทุน ถ้าใช้ end marker แทน ผม/ดิฉันจะต้องสแกนหา marker ใน body ซึ่ง
แปลว่าต้อง escape marker ภายใน body ซึ่งแปลว่า framing ขึ้นกับเนื้อหา นั่นคือกฎที่
ยืนยันว่าจะไม่ยอมละเมิด

**สอง: `content-length` บังคับมีเสมอเมื่อมี body** ฝ่ายรับจึงรู้แน่นอนว่าต้องอ่านกี่ไบต์
และไม่ต้องเดาว่าข้อความจบตรงไหน สิ่งนี้ทำให้ส่งข้อความติด ๆ กันบน connection เดียว
ได้อย่างปลอดภัย และเป็นสิ่งที่ทำให้สตรีมได้ — ผม/ดิฉันอ่านตามจำนวนที่รู้แล้ว ทีละบล็อก
256 กิโลไบต์ ตรงเข้าไฟล์ปลายทาง คำนวณ hash ไปด้วยระหว่างทาง
**ไฟล์สี่สิบกิกะไบต์ใช้หน่วยความจำเท่ากับไฟล์สี่กิโลไบต์**

**สาม: target ใน request line ถูก percent-encode**

`[แสดง: request line สองบรรทัดที่ percent-encode แล้ว จาก DESIGN.md §4.3]`

สิ่งนี้รับประกันว่า request line จะมี **สาม token คั่นด้วยช่องว่างเสมอ** ไม่ว่าไฟล์จะ
ชื่ออะไร ถ้าไม่มีมัน `GET Quarterly Report final.pdf KUFT/2.0` จะถูกแยกเป็นห้า token
และ parse ไม่ผ่าน — ซึ่งเป็นจุดที่เวอร์ชันหนึ่งพังจริง ๆ แต่พอมีมันแล้ว ชื่อไฟล์ภาษาไทย
ก็โอนได้ครบถ้วน

**สี่: ทุกความยาวที่คู่สนทนามีอิทธิพลต่อได้ มีเพดานตายตัว** แปดกิโลไบต์ต่อบรรทัด
ควบคุม หกสิบสี่เฮดเดอร์ control body สี่เมกะไบต์ คู่สนทนาที่ส่งบรรทัดเฮดเดอร์โดยไม่มี
ตัวจบบรรทัด จะทำให้เซิร์ฟเวอร์จองหน่วยความจำไม่จำกัดไม่ได้

และมีกฎเล็ก ๆ อีกข้อที่ปิดช่องโหว่จริง: **ตัว encoder ปฏิเสธที่จะส่งค่าเฮดเดอร์ที่มี
CR หรือ LF** ถ้าไม่มีข้อนี้ ชื่อไฟล์ที่มีตัวขึ้นบรรทัดใหม่อยู่ข้างในสามารถแทรกเฮดเดอร์
ปลอม หรือแทรกแม้กระทั่ง status line ปลอม เข้าไปในคำตอบได้ การปฏิเสธตั้งแต่ตอน
encode หมายความว่าไม่มีผู้เรียกใช้รายไหนเปิดช่องโหว่นี้ได้เลย

### Methods และ status codes — โดยย่อ

`[แสดง: ตาราง method จาก DESIGN.md §4.4]`

เก้า method แต่ละอันจับคู่กับปฏิบัติการบนระบบไฟล์หนึ่งอย่างพอดี และไม่มีอันไหน
ครอบคลุมอันอื่น `HELLO` กับ `AUTH` สำหรับการเริ่มต้น; `LIST`, `STAT`, `GET`, `PUT`,
`DELETE`, `MKDIR`, `MOVE` สำหรับการทำงาน; และ `QUIT` สำหรับปิดอย่างสุภาพ

Status code เป็นเลขสามหลักตามคลาสของ HTTP เพื่อให้ *คลาส* มีความหมายแม้ผู้รับจะ
ไม่รู้จักรหัสเฉพาะตัวนั้น มีรหัสหนึ่งที่เป็นของผม/ดิฉันเองแท้ ๆ คือ
**`422 CHECKSUM MISMATCH`** ซึ่งหมายความว่า *คำขอถูกต้องตามรูปแบบ และข้อมูลมาถึง
ครบตามที่ชั้น transport รับรู้ แต่ payload ไม่ตรงกับ checksum ที่ผู้ส่งประกาศไว้*
ไม่มีรหัส HTTP ไหนหมายความแบบนั้น และนี่คือความล้มเหลวที่สำคัญที่สุดที่โปรโตคอลนี้
ต้องรายงานได้

### กลไกจับคู่ — หัวใจของการออกแบบ

`[แสดง: แผนภาพการดักกลางทางจาก DESIGN.md §4.7]`

ทีนี้มาถึงส่วนที่ภูมิใจที่สุด

**ปัญหาคือ** TLS ให้ช่องทางที่เป็นความลับ — แต่ใบรับรองของเซิร์ฟเวอร์เป็นแบบ
**self-signed** บนเครือข่ายที่มีแค่แล็ปท็อปสองเครื่องไม่มี certificate authority ให้
อ้างอิง ใบรับรองเพียงลำพังจึง *ไม่พิสูจน์อะไรเลย* ผู้โจมตีสร้างขึ้นเองได้ง่ายพอ ๆ กับเรา
และ **การเข้ารหัสไปหาคู่สนทนาที่ไม่รู้ว่าเป็นใคร แทบไม่มีค่า** — มันป้องกันคนที่นั่งฟัง
เฉย ๆ ได้ แต่ไม่ป้องกันคนที่แทรกอยู่ตรงกลางเลย

**แนวคิดหลัก** สรุปได้ประโยคเดียว: **ผูก proof ของการพิสูจน์ตัวตนเข้ากับใบรับรองที่
ถูกนำเสนอจริง**

ทำอย่างนี้ครับ/ค่ะ เซิร์ฟเวอร์พิมพ์ **รหัสจับคู่ขนาดหกสิบบิต** ออกมา เป็นอักขระ
base32 สิบสองตัว แสดงเป็นสามกลุ่ม กลุ่มละสี่ตัว ทั้งสองฝั่งยืดรหัสนั้นด้วย PBKDF2
สองแสนรอบ ให้กลายเป็นกุญแจ `K` จากนั้นไคลเอนต์คำนวณ HMAC ภายใต้ `K` ครอบคลุม
สี่สิ่ง: label หนึ่งตัว, **ลายนิ้วมือของใบรับรองที่มันเห็น**, nonce ใหม่ของตัวเอง และ
nonce ใหม่ของเซิร์ฟเวอร์ เซิร์ฟเวอร์ตรวจสอบ แล้วส่ง HMAC อีกตัวที่ *ต่างกัน* กลับมา
บนข้อมูลชุดเดียวกัน ไคลเอนต์จึงรู้ว่าเซิร์ฟเวอร์ก็ถือรหัสนั้นอยู่เช่นกัน

`[แสดง: บล็อกการสร้าง proof จาก DESIGN.md §4.7]`

**ทีนี้ดูว่าการโจมตีล้มเหลวอย่างไร** ผู้โจมตีแทรกอยู่ตรงกลาง ปิด TLS ทั้งสองด้าน
ด้วยใบรับรองของตัวเอง เรียกลายนิ้วมือของมันว่า `FP'`

ไคลเอนต์คำนวณ proof บน `FP'` เพราะนั่นคือใบรับรองที่มันเห็น ผู้โจมตีส่ง proof นั้น
ต่อไป — มันคำนวณใหม่ไม่ได้ เพราะการคำนวณใหม่ต้องใช้ `K` เซิร์ฟเวอร์ตรวจ proof
เทียบกับ `FP` ซึ่งเป็นลายนิ้วมือของตัวเอง **สองค่าไม่ตรงกัน MAC จึงไม่ตรงกัน และ
เซิร์ฟเวอร์ตอบ 401**

ผู้โจมตีซ่อมสถานการณ์นี้ไม่ได้ถ้าไม่มี `K` และหา `K` ไม่ได้ถ้าไม่มีรหัส —
**และรหัสนั้นไม่เคยวิ่งผ่านเครือข่ายในรูปแบบใดเลย** ไม่ได้เข้ารหัสส่ง ไม่ได้ hash ส่ง
ไม่ได้ส่งเลย คุณอ่านมันจากหน้าจอ

องค์ประกอบอื่นทุกตัวในสูตรนั้นมีไว้กันการโจมตีเฉพาะอย่าง **nonce ใหม่จากทั้งสองฝั่ง** —
proof ที่ถูกดักไว้ใช้ได้กับ connection เดียวและไม่มีวันใช้ได้อีก **label สองอันที่ต่างกัน** —
proof ของไคลเอนต์ถูกส่งย้อนกลับเป็น proof ของเซิร์ฟเวอร์ไม่ได้ **length prefix ในทุก
ฟิลด์** — ทำให้การเข้ารหัสเป็นแบบ injective ไม่มี input สองชุดที่ต่างกันจะให้ไบต์ชุด
เดียวกันเข้าไปคำนวณ MAC **PBKDF2 สองแสนรอบ** — proof ที่ถูกดักได้ให้แค่การโจมตี
offline ต่อหกสิบบิตที่มีการยืดกุญแจอย่างหนักขวางอยู่ **การเปรียบเทียบแบบเวลาคงที่**
ทั้งสองฝั่ง — ไม่มี timing side channel และชุดอักขระ base32 **ไม่มีเลข ศูนย์ หนึ่ง แปด
เก้า** เวลาอ่านรหัสออกเสียง O กับ 0 จึงสับสนกันไม่ได้

**จากนั้นไคลเอนต์ก็ปักหมุด** เหมือน SSH ทุกประการ มันเก็บลายนิ้วมือและกุญแจไว้ และ
การเชื่อมต่อครั้งต่อ ๆ ไปก็เงียบสนิท ไม่ต้องใส่รหัสอีก และถ้าลายนิ้วมือเปลี่ยนเมื่อไร
**ไคลเอนต์จะปฏิเสธการเชื่อมต่อ ไม่มี prompt ให้กด "ดำเนินการต่อ"**

นั่นเป็นการตัดสินใจออกแบบโดยเจตนา ไม่ใช่การลืมใส่ ลายนิ้วมือที่เปลี่ยนหมายถึงอย่างใด
อย่างหนึ่ง: เซิร์ฟเวอร์ถูกสร้างใหม่ หรือคุณกำลังถูกดักอยู่
**และกล่องข้อความให้กดยืนยัน คือวิธีที่คนกดผ่านกรณีหลังพอดี** ดังนั้นจึงไม่มีมัน
การกู้คืนต้องใช้คำสั่งแยกต่างหากอย่างตั้งใจ คือ `kuft.py forget` ซึ่งบังคับให้คุณต้องหยุด
แล้วคิด

### แล้วข้อมูลของคุณเกิดอะไรขึ้นบ้าง

อีกสองการรับประกัน สั้น ๆ

**การดาวน์โหลดลงจอดที่ไฟล์ `.part`** ไคลเอนต์คำนวณ hash ขณะเขียนและเทียบกับ
checksum ของช่วงข้อมูลที่เซิร์ฟเวอร์ให้มา จากนั้น hash ไฟล์ที่ประกอบเสร็จแล้วเทียบกับ
checksum ของไฟล์ทั้งไฟล์ **ทั้งสองต้องผ่าน** ก่อนจะเปลี่ยนชื่อเป็นชื่อจริง ถ้าล้มเหลว
ไฟล์ `.part` จะยังอยู่ — ซึ่งเป็นสิ่งที่ทำให้ครั้งถัดไปทำต่อได้ แทนที่จะเริ่มใหม่

**การอัปโหลดเป็นแบบ atomic** เซิร์ฟเวอร์เขียนลงไฟล์ชั่วคราว *ในไดเรกทอรีปลายทาง*
คำนวณ hash เทียบ แล้ว *จึงค่อย* เปลี่ยนชื่อเข้าตำแหน่ง อยู่ไดเรกทอรีเดียวกัน การ
เปลี่ยนชื่อจึงอยู่ในระบบไฟล์เดียวกันและเป็น atomic และการเปลี่ยนชื่อเกิดหลัง checksum
ตรงเท่านั้น ดังนั้น **การอัปโหลดที่ขาดตอนหรือถูกดัดแปลง ไม่มีทางทับไฟล์ดี ๆ ได้เลย**
ไฟล์เวอร์ชันเดิมรอดโดยไม่ถูกแตะต้อง

`[พิมพ์: python kuft.py connect <ที่อยู่>]`

TLS 1.3 handshake เสร็จแล้ว ทีนี้ — เป็นการติดต่อครั้งแรก มันจึงแสดง
**ลายนิ้วมือที่ถูกนำเสนอมา** และถามหารหัส

> ชี้ที่จอทั้งสอง *"ลายนิ้วมือเดียวกันทั้งสองฝั่ง นี่คือค่าที่จะถูกใส่เข้าไปใน HMAC"*

`[พิมพ์: รหัสจับคู่]`

ข้อความ "deriving key from pairing code" คือ PBKDF2 สองแสนรอบที่กำลังทำงาน และ:
**จับคู่สำเร็จ** ลายนิ้วมือถูกปักหมุดแล้ว นั่นคือครั้งสุดท้ายที่ต้องพิมพ์รหัสนี้สำหรับ
เซิร์ฟเวอร์เครื่องนี้

`[พิมพ์: ls]`

`[พิมพ์: get sample.bin]`

ไฟล์ `.part` จึงถูกเปลี่ยนชื่อเข้าตำแหน่ง ถ้าตัวใดตัวหนึ่งไม่ตรง ไฟล์นั้นจะยังนั่งอยู่เป็น
`.part` และคุณจะได้ `422`

**ทีนี้ส่วนที่สำคัญที่สุด** `[พิมพ์: get ../../../etc/passwd]`

`[พิมพ์: python kuft.py serve --new-code]`

`[แสดง: เทอร์มินัลไคลเอนต์]` `[พิมพ์: python kuft.py connect <ที่อยู่>]`

## §6 — การทดสอบ (1 นาที)

`[แสดง: เทอร์มินัล]` `[พิมพ์: python -m unittest discover -s tests]`

**87 การทดสอบ ผ่านทั้งหมด ใช้เวลาประมาณสิบวินาที** แบ่งเป็นสี่ชั้น

**ชั้น codec โดยไม่ใช้ socket เลย** — การ encode/decode ไป-กลับ, ช่องว่างและ Unicode
ในชื่อไฟล์, body ที่มี CRLF และ NUL, ข้อความติด ๆ กันที่ยังรักษา framing ได้, body
ที่ถูกตัดขาด และการปฏิเสธ framing ทุกกรณี

**ชั้น crypto ก็ไม่ใช้ socket เช่นกัน** — รวมถึงข้อที่สำคัญที่สุด:
**การทดสอบว่า proof เปลี่ยนเมื่อลายนิ้วมือเปลี่ยน** นั่นคือการยืนยันการป้องกันการดัก
กลางทางโดยตรง

**ชั้นการรับรหัสจับคู่แบบซ่อน input** — backspace, ปุ่มลูกศร, Ctrl+C และ fallback
สำหรับเทอร์มินัลที่ไม่มี console

**และชั้น end-to-end บน TLS จริง** — เซิร์ฟเวอร์จริงบนพอร์ตชั่วคราว ขับด้วยไคลเอนต์
จริง รหัสผิด ลายนิ้วมือเปลี่ยน คำขอที่ยังไม่พิสูจน์ตัวตน การดาวน์โหลดไฟล์ข้อความ
Unicode ไบนารี และไฟล์ขนาดศูนย์ไบต์ การ resume checksum ที่ล้มเหลวโดยไม่ทิ้ง
ร่องรอย path traversal ชื่อไฟล์ภาษาไทย rate limit และขีดจำกัดจำนวนไคลเอนต์

ชุดทดสอบเขียนขึ้นให้เป็น **รูปแบบที่รันได้ของข้อกำหนด** — ทุกข้อกำหนดที่มีเลขกำกับ
ในหัวข้อ conformance ของเอกสารข้อกำหนด มีการทดสอบที่จะล้มเหลวถ้าข้อนั้นถูกละเมิด

## §7 — ข้อจำกัดที่ยอมรับตามตรง (45 วินาที)

`[แสดง: รายการนอกขอบเขตจาก DESIGN.md §7]`

มีสี่ข้อที่อยากพูดเอง มากกว่าจะรอให้ถูกถาม

**ไม่มีตัวตนรายบุคคล** มีรหัสร่วมรหัสเดียว ระดับความไว้วางใจเดียว นั่นเป็นระดับพิธีการ
ที่พอดีสำหรับเครื่องสองเครื่องของคนคนเดียว และไม่พอดีสำหรับห้องแล็บ

**ไฟล์ known hosts เก็บกุญแจที่ derive แล้ว** สิทธิ์อ่านไฟล์นั้นจึงเทียบเท่ากับการถือ
รหัสจับคู่ — ระดับความไว้วางใจเดียวกับกุญแจส่วนตัวของ SSH

**ไม่ได้จัดการเรื่องการวิเคราะห์ปริมาณทราฟฟิก** ผู้สังเกตการณ์รู้ขนาดและเวลาของทุก
การโอน แม้จะไม่รู้ชื่อไฟล์หรือเนื้อหา

**และการเพิกถอนสิทธิ์เป็นแบบทั้งหมดหรือไม่เลย** — การหมุนรหัสใหม่เพิกถอนสิทธิ์
ไคลเอนต์ทุกรายพร้อมกัน

ถ้ามีเวลามากกว่านี้: บัญชีผู้ใช้รายบุคคล, การโอนแบบวนลึกทั้งไดเรกทอรี และ mDNS
service discovery เพื่อไม่ต้องพิมพ์หมายเลข IP — และข้อสุดท้ายนั้น service discovery
บังเอิญเป็น **จุดเดียวในโครงงานนี้ที่ UDP จะเป็นคำตอบที่ถูกต้องจริง ๆ**: best-effort,
multicast, ลองใหม่ที่ชั้นแอปพลิเคชัน

## §8 — ปิดท้าย (30 วินาที)

`[แสดง: ตารางสรุปจาก DESIGN.md §10]`

ขอปิดท้ายด้วยคำตอบสี่ข้อ

**ทำมาเพื่ออะไร** — ย้ายไฟล์โดยตรงระหว่างสองเครื่องบนเครือข่ายเดียวกัน เข้ารหัสและ
ตรวจสอบความถูกต้อง ไม่ผ่านบุคคลที่สาม ไม่ต้องมีบัญชี

**ทำงานอย่างไร** — เซิร์ฟเวอร์แบบ multi-thread บน TLS 1.3 แชร์ไดเรกทอรีเดียวที่ถูก
กักขอบเขต ไคลเอนต์จับคู่ครั้งเดียวแล้วปักหมุดใบรับรองแบบเดียวกับ SSH ข้อมูลถูก
สตรีมเป็นบล็อกขนาดคงที่และตรวจสอบด้วย SHA-256 *ก่อน* ที่ไฟล์จะปรากฏภายใต้ชื่อจริง

**ออกแบบโปรโตคอลอย่างไร** — ส่วนหัวที่เป็นข้อความบวก content-length ที่บังคับมี
framing จึงไม่ขึ้นกับเนื้อหาของ body; target ที่ percent-encode แล้ว request line จึงมี
สาม token เสมอ; และ proof ของการจับคู่ที่ใส่ลายนิ้วมือใบรับรองเข้าไปใน HMAC ซึ่งเป็น
สิ่งที่ทำให้การเข้ารหัสมีความหมายจริง ๆ

**และใช้ transport service model แบบไหน** — **TCP**: connection-oriented, เชื่อถือได้,
เรียงลำดับ, ไม่ซ้ำ, เป็นสตรีมไบต์ พร้อม flow control และ congestion control ไฟล์
ต้องการทุกไบต์ ครั้งเดียว ตามลำดับ — ซึ่งตรงกับรายการสิ่งที่ TCP รับประกันพอดี
การสร้างสิ่งเหล่านั้นบน UDP คือการเขียน TCP ใหม่ให้แย่ลง และ TLS มีให้ใช้บน TCP
ในไลบรารีมาตรฐาน ขณะที่ DTLS ไม่มี การเลือก UDP จึงเท่ากับต้องเขียนวิทยาการรหัสลับ
เอง หรือไม่มีการเข้ารหัสเลย

**ส่วนที่ TCP ขาด ผม/ดิฉันเติมเอง และสิ่งเดียวที่มันขาดจริง ๆ — การไม่รับประกันเรื่อง
เวลา — ไม่เสียหายอะไรเลย เพราะในการรับส่งไฟล์ ไบต์ที่มาช้ามีค่าเท่ากับไบต์ที่มา
ตรงเวลาทุกประการ**

ขอบคุณครับ/ค่ะ ยินดีรับคำถาม

## เตรียมตอบคำถาม

อ่านส่วนนี้ก่อนขึ้นนำเสนอ คำตอบส่วนใหญ่ยาวหนึ่งถึงสองประโยค อย่าตอบยาวเกิน

**"ทำไมไม่ใช้ HTTPS หรือ FTP หรือ SFTP ไปเลย"**
โจทย์คือให้ออกแบบโปรโตคอลชั้นแอปพลิเคชัน การหยิบของสำเร็จรูปมาใช้จึงผิดวัตถุประสงค์
แต่มีเหตุผลจริงด้วย FTP ใช้ **สอง** connection — control connection กับ data connection
แยกกัน ที่ต้องเจรจาด้วย `PORT` หรือ `PASV` ซึ่งเป็นปัญหาคลาสสิกกับ NAT และไฟร์วอลล์
ส่วน KUFT ใช้ connection เดียว HTTP ไม่มีแนวคิดของ session ที่มีสถานะและพิสูจน์
ตัวตนแล้ว จะใช้ก็ต้องเอากลไกจับคู่ไปแปะเพิ่มอยู่ดี และ SFTP ต้องมี SSH server กับ
บัญชีผู้ใช้บนเครื่องปลายทาง ซึ่งเป็นข้อกำหนดเบื้องต้นที่หนักกว่า "รันสคริปต์นี้" มาก

**"TLS อย่างเดียวไม่พอหรือ ทำไมต้องมีรหัสจับคู่ด้วย"**
ไม่พอครับ/ค่ะ และนี่คือประเด็นสำคัญที่สุดของโครงงาน TLS ให้ช่องทางที่เป็นความลับ —
กับ *ใครสักคน* ใบรับรองเป็น self-signed บนเครือข่ายที่ไม่มี certificate authority
มันจึงไม่พิสูจน์อะไรเลย ผู้โจมตีสร้างขึ้นเองได้ง่ายพอ ๆ กัน ถ้าไม่มีรหัสจับคู่ TLS จะ
ป้องกันได้แค่คนที่นั่งฟังเฉย ๆ และ **ไม่ป้องกันคนที่แทรกอยู่ตรงกลางเลย** รหัสจับคู่คือ
สิ่งที่เปลี่ยน "เข้ารหัสแล้ว" ให้เป็น "เข้ารหัสถึงเครื่องที่ถูกต้อง"

**"ถ้าผู้โจมตีดัก proof ไว้แล้วส่งซ้ำล่ะ"**
ทั้งสองฝั่งใส่ nonce ใหม่ขนาด 32 ไบต์เข้าไปในทุก connection และ nonce ทั้งสองตัวอยู่
ภายใน HMAC proof ที่ถูกดักไว้จึงใช้ได้กับ connection นั้นครั้งเดียวและไร้ค่าหลังจากนั้น

**"หกสิบบิตก็ไม่มากนะ เดารหัสไม่ได้เหรอ"**
เดาแบบ online ไม่ได้ — รหัสผิดจะโดนหน่วงหนึ่งวินาที การเดาจำนวนมากจึงเป็นไปไม่ได้
ส่วนแบบ offline กับ proof ที่ดักไว้ ต้องเจอหกสิบบิตที่มี PBKDF2 สองแสนรอบขวางอยู่
ซึ่งเกินกว่าที่ใครจะยอมลงแรงเพื่อไฟล์แชร์ในบ้าน และถ้ากังวล `--new-code` หมุนรหัสใหม่ได้

**"ทำไมไม่ใช้ UDP เพื่อความเร็ว มันเร็วกว่าไม่ใช่หรือ"**
เร็วกว่าก็ต่อเมื่อคุณไม่สนใจว่าไฟล์จะถูกต้องหรือไม่ วินาทีที่คุณเพิ่ม acknowledgement
และ retransmission เข้าไปเพื่อให้มันถูกต้อง คุณก็ได้ต้นทุนเท่า TCP บวกกับการ implement
ที่แย่กว่า และบน LAN ที่อัตราการสูญหายเกือบเป็นศูนย์และ RTT ต่ำกว่าหนึ่งมิลลิวินาที
overhead ของ TCP ไม่ใช่คอขวดอยู่แล้ว — ดิสก์ต่างหากที่เป็น

**"ไฟล์ใหญ่กว่าหน่วยความจำจัดการยังไง"**
ทุกอย่างสตรีมทีละบล็อก 256 กิโลไบต์ และคำนวณ hash แบบสะสมไปพร้อมกับบล็อกที่
ไหลผ่าน ไม่มีจุดไหนในโค้ดที่โหลด payload ทั้งก้อนเข้าหน่วยความจำเลย ไฟล์สี่สิบ
กิกะไบต์ใช้หน่วยความจำเท่ากับไฟล์สี่กิโลไบต์

**"ถ้าการเชื่อมต่อขาดกลางคันตอนดาวน์โหลดล่ะ"**
ข้อมูลที่ได้มาแล้วยังอยู่ในไฟล์ `.part` สั่ง `get` เดิมซ้ำอีกครั้ง ไคลเอนต์จะส่งเฮดเดอร์
`range` พร้อมตำแหน่งไบต์ที่มีอยู่แล้ว เซิร์ฟเวอร์ seek ไปตรงนั้นและตอบ
`206 PARTIAL CONTENT` จากนั้นมันตรวจ checksum ของ *ไฟล์ที่ประกอบเสร็จทั้งไฟล์*
ไม่ใช่แค่ส่วนใหม่ การโอนที่ทำต่อจึงถูกตรวจสอบเข้มงวดเท่ากับการโอนครั้งแรก

**"TCP มี checksum อยู่แล้ว ทำไมต้องมี SHA-256 อีก"**
สามเหตุผลครับ/ค่ะ หนึ่ง มันคือผลรวม one's-complement 16 บิตที่ออกแบบมาจับสัญญาณ
รบกวน จึงอ่อนแอ สอง มันคำนวณต่อ segment และ **ถูกคำนวณใหม่โดยอุปกรณ์กลางทาง
ทุกตัว** การแก้ไขของผู้โจมตีเชิงรุกจึงผ่านฉลุย และสาม มันไม่บอกอะไรเลยเกี่ยวกับสิ่งที่
ดิสก์ฝั่งรับเขียนลงไปจริง ๆ end-to-end argument บอกว่าการตรวจสอบเดียวที่มีความหมาย
คือการตรวจสอบที่ปลายทาง ผม/ดิฉันจึงตรวจที่ปลายทาง

**"เซิร์ฟเวอร์แบบ thread ต่อ connection ปลอดภัยไหม ถ้าโดนถล่มด้วยไคลเอนต์จำนวนมาก"**
มี semaphore จำกัดไว้ที่แปด session พร้อมกันเป็นค่าเริ่มต้น ปรับได้ ไคลเอนต์รายที่เก้า
จะได้ `503` อย่างถูกต้อง ส่งภายใน **TLS** จึงเป็นการตอบตามโปรโตคอลจริง ไม่ใช่การ
ตัดการเชื่อมต่อทิ้ง นอกจากนี้ยังมี rate limiter ต่อ connection ที่ตอบ `429` พร้อม
`retry-after` และทุก socket มี timeout 300 วินาที ไคลเอนต์ที่หายไปจึงคืนช่องว่างให้ระบบ

**"ทำไมใช้ thread ต่อ connection แทน async"**
session ที่นี่มีอายุยาว มีสถานะ และถูกครอบงำด้วย blocking I/O บน socket และไฟล์
ที่แปดไคลเอนต์พร้อมกัน event loop ไม่ให้ประโยชน์ที่วัดได้เลย แต่แลกด้วยความซับซ้อน
มาก ถ้าเป้าหมายคือหมื่น connection คำตอบจะเปลี่ยนไป

**"ไคลเอนต์อ่านไฟล์นอกโฟลเดอร์ที่แชร์ได้ไหม"**
ไม่ได้ ทุก target ถูก resolve แล้วตรวจเทียบกับ share root และ `resolve` ยุบ `..`
**และตาม symlink ก่อนการตรวจสอบ** symlink ที่ชี้ออกนอกจึงถูกปฏิเสธเหมือน `../`
ตรง ๆ ซึ่งเป็นสิ่งที่การเทียบ prefix ของสตริงแบบง่าย ๆ จะพลาด คำตอบคือ `403`
ไม่ใช่ `404` มันจึงไม่รั่วข้อมูลว่า path ข้างนอกมีอยู่จริงหรือไม่ และมีการทดสอบข้อนี้ด้วย

**"ทำไมใช้พอร์ต 5150"**
มันสูงกว่า 1024 จึงไม่ต้องใช้สิทธิ์พิเศษ และอยู่นอกช่วงที่มีการจดทะเบียนของบริการ
ทั่วไป ปรับได้ด้วย `--port`

**"ใช้ข้ามอินเทอร์เน็ตได้ไหม ไม่ใช่แค่ LAN"**
ตัวโปรโตคอลได้ — ไม่มีอะไรในนั้นที่สมมติว่าต้องเป็นเครือข่ายภายใน แต่ NAT traversal,
service discovery และการเพิกถอนสิทธิ์อยู่นอกขอบเขตทั้งหมด ในทางปฏิบัติจึงต้องทำ
port forwarding มันถูกออกแบบมาสำหรับ LAN

**"จุดอ่อนที่ใหญ่ที่สุดคืออะไร"**
รหัสจับคู่ที่ใช้ร่วมกันเพียงรหัสเดียว ไม่มีตัวตนรายบุคคล ทุกคนที่มีรหัสจึงมีสิทธิ์เท่ากันหมด
และการเพิกถอนสิทธิ์ไคลเอนต์รายเดียวหมายถึงการเพิกถอนทุกราย สำหรับเครื่องสองเครื่อง
ของคนคนเดียวนั่นคือการแลกที่เหมาะสม สำหรับห้องแล็บไม่ใช่ และการแก้ให้ถูกต้องต้องมี
ตารางผู้ใช้และ salt รายคน
